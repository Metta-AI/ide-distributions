Autoresearch on Softmax Hosting

This plan puts the autoresearch agent into Rohit's hosted Hermes fleet. As a result, a coach who clicks Start Hermes in the Softmax IDE gets autoresearch. We wrote it for James from plan revision 5 and Rohit's update of 2026-10-09. We checked the metta facts against main at 0c0752ed3f.

Executive Summary

Today a coach who clicks Start Hermes in the Softmax IDE gets Rohit's optimizer profile. We want that coach to get the autoresearch agent in a hosted workspace that is always on. In that workspace, the agent does its research loop, answers in IDE chat, and takes work from the IDE research buttons. The coach can also pause and resume it. Autoresearch already works on our own EC2 test box, and it submitted its first league champion there. Rohit made and deployed the hosted system. It is a shared EC2 fleet, and each player gets a Hermes sandbox that connects to the IDE. Today the fleet operates his rohit-optimizer profile on one small host with $10 inference keys. Rohit is away for the next few days, thus we own his code and the deployment for now. Our agents write and land the metta changes. Aaron, Alex and Richard review them, and James operates the infrastructure.

The plan has six milestones. M0 is prerequisites. M1 is a full local run on a Lima VM. M2 is the first hosted deploy with Gods of the Arena (GotA). M3 is GotA research with the compiler. M4 lets us update the profile without a host replacement, and M5 adds more hosts. One fact controls the whole plan: every deploy replaces the host and erases the workspace files. The files stay only if an operator copies them to the new host first. Also, the new sandbox size leaves two slots for all of softmax.com until M5. Status: we made the decisions, and Tasks 1 and 2 are done and in review as PR #21 (jboggs/autoresearch-hosted-m1a). We have not built anything else. M0 and M1 are next.

1 · Rohit's system in 10 minutes

  • The IDE asks the Softmax API for a workspace. The API writes an encrypted record to S3. Then a controller on one EC2 host reads S3 and starts one gVisor sandbox for each player.
  • One host is live: hermes-rohit-validation. It is an m7i.2xlarge with room for a maximum of 8 workspaces of 2 CPU / 2 GiB / 10 GiB each. All of them operate rohit-optimizer.
  • A change to the image, the controller or the sizes replaces the host. The records stay, but the workspace files do not, unless an operator moves the disks.
  • Rohit made sure that the simple path for one user works. He did not test a new signup, two users on one host, or the recovery of a host.

This section is for a reader who starts with no background. It shows how the click of a coach becomes a live agent. It also shows what is deployed today, how a deploy works, and where the evidence is weak. A glossary at the end gives the meaning of the terms that the rest of the document uses.

The request flow

When a coach clicks Start Hermes, these events occur in this sequence:

  1. The IDE calls the API. The Hermes routes of the API are start, status and bridge report only. No route erases a workspace1. A user can have only one hosted player, and the API refuses a second allocation with HTTP 4092.
  2. The API makes a workspace. It makes a new cga_ player token3 and an OpenRouter key from a global budget of $10 for 30 days4. The token is a new agent credential for the player that the coach selected in the IDE. The API does not make a new player. Then it writes the workspace record, which holds those secrets, to S3 and not to the host5.
  3. The host controller finds the record. The controller is fleet.py, a systemd service on the EC2 host. It reads S3 each 15 seconds. For each record of its host, it makes the disk if the disk is absent. Then it writes runtime.json (the settings of the bridge), pins the container image, and starts the sandbox6. When there are more records than max_workspaces, the oldest records operate. The others stop and show "Waiting for host capacity"7.
  4. The sandbox starts Hermes. In the sandbox, runtime.py installs the profile. Then it starts one Hermes gateway and the bridge89. The bridge must report to the API in 3 minutes or less10.
  5. The bridge connects the IDE to Hermes. It sends IDE chat to Hermes runs. It can also send IDE research tasks into workspace/comms/ files, and it can send the notes of the agent back as task updates. But that relay is off today11.

What is deployed

  • One host: hermes-rohit-validation, instance in AWS account . It is an m7i.2xlarge with 8 vCPU, 32 GiB RAM and a 200 GiB gp3 root disk1213.
  • Host configuration: Terraform gives only image and softmax_server, thus the defaults in the code apply. These are a maximum of 8 workspaces, each with 2 CPU, 2 GiB RAM and a 10 GiB disk. The chat model is openai/gpt-6-luna1415.
  • Profile: each workspace installs rohit-optimizer as the Hermes profile with the name optimizer. The image pins it at commit f6508fb, and the research relay is off16811.

How a deploy works, and why it erases workspaces

  1. Make the runtime image and push it to ECR (the container registry of AWS). Make the host bundle and upload it to S3 with a new key. Nobody overwrites that key17.
  2. Set runtime_image, bundle_key and bundle_sha256 in Spacelift (the hosted service that operates our Terraform). Then apply.
  3. Terraform sets user_data_replace_on_change. As a result, a change to the image, the controller or the sandbox sizes replaces the full host. The host also has prevent_destroy, which is there to stop that replacement18. Rohit's #27146 replaced the host "with explicit approval". Nobody wrote down how that replacement got past prevent_destroy19.
  4. The new host reads each S3 record for its host id. When the disk of a record is absent, the record gets a new, empty disk and the current image of the host6. Thus the records stay after a replacement, but the workspace files do not. The files stay only if an operator copies the disks to the new host first. That copy is the "move" procedure. It does not exist yet, and we will write it.
  5. The runtime never updates a profile after it installs it20. Also, the controller pins the image of each workspace at its first start21. Thus a live workspace gets new code only through a host replacement or a move.
Why this controls the whole plan Each deploy in M2 thru M4 is a host replacement. Each one is an outage that users can see, and it empties each disk that we do not move. When the sandboxes get larger, the host also goes from 8 slots to 2. M4 is there so that a profile update does not need a replacement.

2 · What changes to run autoresearch there

  • We put our profile into the runtime image as a pinned archive that the build checks. The reason is that the sandbox must never hold a GitHub credential.
  • The profile installs with the name of Rohit's profile, optimizer, thus no route changes. When an update fails, the runtime keeps the old profile and does not restart in a loop.
  • We set the task relay of the bridge to on. The bridge also learns to report failed and blocked work correctly.
  • Sandboxes grow to 8 CPU / 16 GiB / 100 GiB, with two on each host. Each key grows from $10 to $500 each week, with a weekly reset.

Each change in the table is small. Together, the changes turn Rohit's general runtime into one that operates our research loop safely and without a stop. The "Why" column gives the reason that we cannot omit each change.

M4 · Profile updates without host replacement

Goal: a new autoresearch commit gets to the live workspaces with one container restart and no loss of state46.

Shape: a pin with a KMS signature, plus a tar file, in an S3 prefix that only the operator can write. The controller checks the signature, unpacks the tar safely, and checks the tree id. Then it changes a symlink and restarts each container at a quiet time. The current update path of the runtime applies the new profile.

Done when: a profile update is an S3 upload.

Cost and rollback: M4 needs one more host replacement to ship, because it changes the controller and the permissions of the host. If the check fails, the old profile stays current. This milestone is the repair for D6.

Decided · D9 Inbox trust (alternative a accepted)

Question. Each process in a sandbox operates as uid 10000. This includes the gateway, the bridge, the chat and the research workers15. Thus any research code can write the inbox of the coach, commit to the canonical workspace, or start comms inbound. It can do all of these with the authority of the coach. Users stay isolated from other users. The only question is this: can research code in one workspace act as the coach of that workspace?

Recommendation. Accept the risk for the first hosted deploy, and write it in the hosting documents. Next step: send coach requests through the API (alternative d). Then queue-keeper reads the task records that the coach wrote from the Softmax API. It trusts the author_role that the server records on the revision that made each record53. Later revisions can be updates that the bridge makes as the cogent54. With this change, a worker that holds the cga_ token can write only as the cogent. Thus it cannot make false coach requests.

Alternative (b) puts only the bridge under a different user. We think that it is not worth the work, because it gives little protection, and it is possible that it does not work under gVisor. Sandboxes with many users (alternative c) are the boundary for the long term.

What it blocks. Nothing in M2. Until alternative (d) ships, it blocks trust in the research results and a larger rollout. The spike of Task 26 gives data for this decision. We must also find out if the player API shows author_role.

6 · Risks and unknowns

  • The largest operational risk is the host replacement. Disks become empty, and 8 slots become 2. Thus, without a cleanup first, it is possible that the workspace of James gets no slot.
  • The largest security risk is the single uid. Research code can act as the coach and read the credential. The persona, the pause and the proposals are not security controls.
  • Each key has a money limit of $500 each week, and our cap is $100 each day. But the cga_ token never expires, and the key does not limit credits or submissions.
  • Each of the seven unknowns has a task that checks it.

Risks

The plan has a mitigation for each risk in this list55.

  • Host replacement and slots. Each deploy is a host replacement. The records come back with empty disks, and the change from 8 slots to 2 stops the newer workspaces7. It is possible that the workspace of James gets no slot, unless we clean up the older records first.
  • Slow deploys and rollbacks, if prevent_destroy needs one PR to remove it and a second PR to put it back.
  • Two slots for all users on softmax.com until M5.
  • The cga_ token never expires. Also, the players of other users have no limits until their coach sets Controls27. The $500 weekly key limits only model spend, and not credits or submissions.
  • One uid (D9 alternative a). Research code can act as the coach, read the .env file (credential and key), and control the local chat API. Start on request, pause, proposals and the persona are not security controls.
  • The chat configuration fails open. If it does not load, chat gets the default tools of Hermes. But the tool allowlist of the plugin still blocks them.
  • Money. A key can spend a maximum of $500 each week, thus approximately $2,140 in its 30 days. One host with two keys can spend a maximum of $1,000 each week. At our cap of $100 each day, a workspace can spend the full $500 in 5 days. The key expires after 30 days, and nothing makes a new one. Each erase and new creation of a record adds one more key.
  • D4. Starters that nobody reviewed can go into the league. Also, the agent can spend credits up to dailyCredits.

7 · Alternatives considered

  • Most of the alternatives that we did not use changed more of the code of Rohit for no gain. Others spent money or broke users that work before a coach asked.
  • We did not refuse two alternatives, but we put them off until later. These are a second host stack for deploys that erase nothing, and research workers with their own uid.

D2 · Profile name

One alternative was to install as autoresearch with a /p/autoresearch/ route. James refused it, because three metta route constants change and we get nothing. When we install as optimizer, the routes of Rohit and the IDE do not change. The cost of this decision is that our profile must not think that it knows its own name (Task 27).

D3 · Activation

Our current behavior is to start research immediately after the install. We refused this alternative, because any softmax.com user can click Start Hermes. Thus a loop that is always on spends money before a coach asks. Decision: start on request.

Budget

One alternative was to keep $10 for 30 days and make the agent smaller, with cheaper models and lower limits. James refused it, because a cheap prototype that does not work gives no baseline. A second alternative was an override for research players only, with a small API change. James then decided on a global $150 for all users, and that decision replaced the override. Later on 2026-10-09, James increased the global key to $500 each week.

For the weekly budget, one alternative was a $500 key that expires after 7 days (HERMES_INFERENCE_KEY_DAYS set to 7). We refused it, because nothing makes a new key after a key expires. Thus each workspace stops after one week. Decision: a weekly reset on a 30-day key.

D6 · Deploy of a new image

For now, we replace the host in its position, and the state is lost unless we move it. A second host stack, with the API then set to it, erases nothing. But it costs 3–4 infrastructure PRs, and one of them changes the production Observatory stack. Thus we put it off until later. We refused an in-place docker pull over SSM, because it does not agree with the model of the fleet README. The repair for the long term is M4. In M4, the host gets profile archives from S3 and applies them in position at a restart, with no host replacement.

D7 · Chat

One alternative for v1 was a smaller chat that can only read. In it, coaches send work only through the IDE buttons. James refused it, because the chat is the main interface of the coach. Also, the typed confirm design already makes it safe to send work. Decision: full coach chat.

D9 · Inbox trust

We looked at four alternatives:

  • (a) Accept the risk for the prototype. We chose this for the first hosted deploy.
  • (b) The bridge as a different OS user, with AUTORESEARCH_INBOX_WRITERS. We refused it as not worth the work. A worker with the same uid can still make false requests through a git commit or comms inbound. Also, under gVisor it needs a second sandbox or the ability to change users. It is possible that a second sandbox cannot get to the gateway. A change of user does not agree with the dropped capabilities and no-new-privileges of the sandbox15.
  • (c) Research workers under a different uid. This is the real boundary for the long term, but it is a large change to both runtimes.
  • (d) The API sends coach requests, and we trust the author_role that the server records53. This is the next step that we recommend.

D12 · Host size

One alternative was to keep the m7i.2xlarge with three sandboxes of 4 CPU / 8 GiB / 50 GiB. James asked for larger sandboxes, and that request replaced this alternative. Two sandboxes on an m7i.2xlarge are too small for 8 / 16 / 100. Decision: an m7i.4xlarge with two sandboxes of 8 CPU / 16 GiB / 100 GiB.

D14 · First deploy

One alternative was to deploy M1 (the fake game) to the fleet. We refused it, because it changes the optimizer agent of each hosted user into a fake-game agent until M2. Decision: M1 stays local, and the first hosted deploy has the GotA settings.

Packaging

One alternative was to clone ide-mvp when the runtime starts. We refused it, because it needs a GitHub credential in the sandbox. Decision: a pinned git archive in the image, which the build checks against a lock file.

How we identify our installed profile

One alternative was to identify it by the name in distribution.yaml. We refused it, because Hermes changes name to the install name during each install and update52. As a result, both profiles show optimizer. Decision: our commit marker, or the recorded install source: path.
