# Orchestrator

A Hermes profile that leads research for one player/game and delegates implementation to
native Kanban researchers on the explicitly named `autoresearch` board. API chat and cron
turns expose only the `orchestrator` toolset. The supervisor is an agent cron job whose
minute preflight skips the model when nothing needs attention.

## Install and configure

Requires Hermes v0.21.6, Python 3.12 for this distribution, uv and Git.
The pinned Hermes runtime itself uses Python 3.14; use its provisioned interpreter for
the `hermes` tests, independently of this profile's Python 3.12 venv. Hosting prepares the bare canonical
repository, this profile's main clone, researcher profiles/clones, the board and native
dispatcher. Clone origins must point to that local bare repository. Use a clean export,
not a checkout containing `.venv`, when installing:

```sh
git archive HEAD orchestrator | tar -x -C /path/to/empty-export
hermes profile install /path/to/empty-export/orchestrator --name orchestrator --yes
```

Set the installed profile's `.env` with `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`,
`SOFTMAX_PLAYER_CREDENTIAL`, `COGAMES_API_URL`, `RESEARCH_PLAYER_ID`, `RESEARCH_GAME`,
`RESEARCH_WORKSPACE` (this profile's clone) and `RESEARCH_CANONICAL` (the bare repo).
The manifest documents defaults. The credential accepts a bare token or player-session
JSON. Hermes's routed profile secret scope supplies HTTP/CLI credentials; a different
profile's ambient credential is not used. Gate subprocesses get the configured passthrough.

The first research call or gate run syncs `$HERMES_HOME/local/venv` from `uv.lock`.
The shared `ide_research_core` package and ontology/game assets are generated by the parent
repository's shared sync step, owned by the parallel researcher implementation. Until those
assets are assembled, CLI-backed tools require the shared package and fail if it is absent;
this branch tests that boundary with a contract fixture, not an alternate research engine.
The runtime dependency list follows autoresearch because the shared package carries that stack.

The installed supervisor starts paused. Hosting should resume it once after preparation,
preserving later deliberate pauses. With the host root selected:

```sh
hermes -p orchestrator cron resume supervisor
```

Configure the host dispatcher with `dispatch_profiles: [researcher-1, ...]`,
`max_in_progress` equal to researcher count, and `max_in_progress_per_profile: 1`.
Connect the IDE bridge to the orchestrator profile's API session. A coach chat reply is
published by the bridge; only background wake/cron turns call `ide_say`.

## Tools

| Tools | Behavior |
|---|---|
| `ide_say(text, key, goal_id?)` | POST a chat line with a stable event key, normally `say:<table>:<rowid>`. |
| `ide_task_update(task_id, patch)` | PATCH an IDE task with `set`, observed `base_rev`, and stable `idempotency_key`. |
| `card_create` | Prepare the assignee clone/branch and create native worktree work; return actual subscription status. |
| `card_show`, `card_list` | Read native cards, runs and comments. |
| `card_comment`, `card_answer` | Durable comment; answer additionally unblocks. |
| `card_close` | Native done with nonempty summary/metadata, or archive; never forces completion of a live claim. |
| `board_reconcile` | Unhandled events/comments, pending platform transitions and branch recovery work. |
| `event_ack(ids)` | Mark table/id pairs handled after acting. |
| `status` | Cards by state, canonical record summary, durable pause and promotion state. |
| `records_find`, `records_show` | Shared canonical record reads. |
| `plan_write`, `control_write` | Publish plan.md or pause/resume through shared workspace publish. |
| `promotion_submit(experiment)`, `bootstrap_champion(version)` | Shared promotion workflow; bootstrap requires the integrated starter version record (`V-...`). |
| `accept_champion()` | Record the league's current champion after the user confirms. |
| `workspace_integrate(branch)` | Shared integration of a pushed card/repair branch. |
| `xp_status(experiment)`, `credits`, `leaderboard` | Shared platform reads. |

`card_create` requires `kind`, `entity`, `assignee`, `title`, `body`. Optional `attempt`
defaults to 1; `refs`, `skills`, `parents` default empty; native priority defaults 0 (higher
runs first), runtime 7200 seconds, failure limit 2 (one retry). Its key is
`<kind>:<entity>:<attempt>`. Entities are record IDs or git-safe keys containing letters,
digits, underscores and hyphens. The branch is `card/<kind>-<entity>-<attempt>`.
A replay returns the same card, including an archived card. A new open card for the same
entity is refused. The per-profile plugin DB serializes creation across sessions.

For repairs, use kind `repair`, a distinct repair entity, and the failed pushed `card_sha`;
the branch prefix is `repair/` and parent links are omitted. Put lineage and failure details
in the body. The assignee's `.env` can override its clone with `RESEARCH_WORKSPACE`; otherwise
its `workspace/` is used. Existing orphan branches from an interrupted create are reused.

The only plugin table is `handled`, keyed by table and row ID. Events/comments are never
acknowledged on observation. Only Hermes's decision events are surfaced: completed, gave_up,
crashed, timed_out, blocked, review_requested, changes_requested and block_loop_detected.
Comments are surfaced only when their author is not the orchestrator. Bookkeeping events and
the orchestrator's own comments never need an ack. Pending waits use the latest ended handoff's `task_runs` ID:
`awaiting.xp` holds request IDs with `experiment.id`; `awaiting.credits` is true; or
`awaiting.permit` is a cogents ask key. Act before acknowledging that run. A lost plugin DB
replays events; card keys, canonical promotions and git ancestry support recovery. An XP wait
without `experiment.id` appears as `bad_handoff` with that run ID; fix or arrange the missing
handoff work, then acknowledge the run.

The gate polls XP terminal status, a positive available credit balance, and permit answers.
Permit answers use the cogents `c/asks/{id}` GET because the shared softmax CLI has no
single-ask read. Every wall-clock ten-minute boundary the gate calls shared `promotion status`,
which advances an in-flight promotion one step. It wakes only when the canonical champion
changed during recovery or there is a conflict and canonical `control/pause.json` is not
already paused. An unchanged in-flight promotion does not wake the model. It keeps no tick
counter, ledger or deadline. Native errors remain errors; the scheduler owns gate-output
handling. `board_reconcile` checks done/unmerged and non-running/merged branches only for
cards with an unacknowledged actionable event or comment in that reconcile. Native live-claim
protections remain in effect. Once the plugin table exists, gate reads do no schema writes,
so a card creation holding its write lock during Git fetch does not block the gate.

For a fresh installation, have a researcher upload the starter with `softmax upload-bootstrap`
and integrate its version record, then call `bootstrap_champion(version="V-...")` to submit it.
On a champion conflict, pause research with `control_write`, explain the disagreement to the
user, and call `accept_champion` only after they confirm accepting the league's champion.
A league champion never recorded by the loop is a conflict, including on migrated hosts.

## Development and verification

```sh
cd orchestrator
uv run pytest -q
uv run pytest -q -m hermes
uv run ruff check .
```

Default tests use local Git repositories, a local HTTP server and a subprocess CLI fixture;
no model or platform credentials are required. Hermes tests use its installed interpreter,
a temporary host root and real native board APIs. Set `HERMES_PYTHON` if Hermes's launcher
does not identify its interpreter. The clean-install test exports committed HEAD, so commit
before running that test. Hosted bridge delivery and shared-package assembly are separate
integration checks; these tests do not establish either one.
