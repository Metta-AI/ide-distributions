Fix plan · November 3, 2026 · Proposed

Follow the canonical Coworld version, and tell the Orchestrator when an invariant breaks

A fix plan for the ide-distributions research profiles (core, orchestrator, researcher), from the repair work on the Nov 2, 2026 runaway-spend incident.

Executive Summary

On Nov 2, 2026, a hosted workspace spent its $10 key in 27 minutes. About half went to 14 wakes (Orchestrator model runs that the watcher starts) from the champion-sync step. First, the workspace pins one Coworld version forever. The leagues follow each new canonical version, so the workspace falls behind within hours, and every comparison by version id breaks. Second, a watcher step that finds a broken condition frequently skips with no signal to the Orchestrator.

The plan has three parts. Part A, in PR #153, is a stopgap: champion sync joins leagues by Coworld name. Part B keys each workspace Coworld by name and makes the watcher follow the canonical version. A new version updates the Coworld in place and starts one debounced upgrade wake. Part C repairs the code bugs that hide failures and adds deduplicated alarms for breaks from outside. The largest cost is a migration that re-keys every store row that names a Coworld.

1 · Problem 1: the workspace pins one version, and a new version wipes everything
  • Leagues follow the canonical version of a Coworld. The workspace keys everything by the one version id that it switched to.
  • No code updates a Coworld to a new version. A switch to a new id makes a new, empty Coworld and a full setup wake.
  • On Nov 2, no league matched the pinned id, and a fallback to every league started 14 wakes.

A Coworld is a game on the Softmax platform, with its own leagues. Every version is its own cow_ id under one Coworld name. generals-competition has 25 versions, and seven came out between Nov 2 at 10:19 AM PST (0.6.3) and Nov 3 at 11:58 AM PST (0.7.3).

A league with an admin game-version lock keeps the version from lock time1. A league's game.coworld_id is the version that it runs, and game.coworld_name is the Coworld name. A game also carries canonical_coworld_id2.

The workspace (the hosted research environment) stores the exact version id that it switched to. The Coworld folder has the name of that id3. The registry row uses it as the key, and Sessions (agent conversations) have an index on it4. The folder holds the code repository, source checkout, worktrees, documents and record store (state/store.db)5.

workspace.coworld_switch takes a version id6. The Orchestrator (the agent that plans research and gives Tasks to Researcher agents) calls it, or the bridge's store apply allow-list sends it to research coworld switch7. Nothing in metta calls it, so the pin is in ide-distributions (the harness), not in the client.

No code path updates a Coworld to a new version. A switch to a new id makes a new, empty Coworld, with a new folder, code repository and record store (Appendix A shows how a switch works). It starts a full setup wake (about $3.20 on Nov 2), and Researcher work stops until the workspace switches back8.

On Nov 2, champion sync (the watcher step that reads league results) matched leagues by exact version id11. None of the three Generals leagues (Build 1v1, FFA, Classic 1v1) matched, so the code used every league on the platform and started the 14 wakes.

The platform still runs old policies after a version change, but a new version can break them. Thus the agent must know about each change, to check its policies.

2 · Problem 2: when an invariant breaks, the watcher goes silent
  • Watcher step errors and notes reach nobody, and the heartbeat stays fresh while other steps fail.
  • A read of every watcher step found 12 silent failures, and five are code bugs.

The watcher is a Hermes cron job that operates every minute12. When a condition is false, many steps skip, and nothing tells the Orchestrator. Three mechanics make this systematic:

  • tick.run_step turns a step's exception into {"error": …} in printed JSON and exits 0. Nothing stores it, so the doctor (the workspace health check), the briefing (the status text for the Orchestrator) and notices never see it13.
  • ctx.note() adds to a list that nothing reads14.
  • Each tick writes the heartbeat first, so the doctor's heartbeat check finds only a watcher that does not operate15.

Notices reach the user on the next chat turn only. Only management wakes (recovery.failed, merge.failed, wake.failed, store.*) wake it, and they need the runs API (the gateway interface that starts model runs)16. Table 1 ranks the silent failures by likelihood times damage.

3 · Part A: join leagues by Coworld name (PR #153)
  • Champion sync joins leagues by game.coworld_name, not by version id. The fallback to every league stays removed.
  • No league with the active Coworld's name gives one deduplicated notice and a briefing line, and no wake.
  • A league on a different version still syncs, with one "workspace is behind" notice for each version pair, and no wake.

A separate agent does this work now, as a stopgap. Under Part B, a version difference lasts one check interval at most, so these notices become rare.

4 · Part B: the workspace follows the canonical version
  • A workspace Coworld has its name as its key. The current version is a field, and a switch always lands on the canonical version.
  • Every 10 minutes the watcher reads the canonical version. A new one starts an upgrade in place that keeps all records.
  • One debounced upgrade wake then checks the policies on the new version.

B1 · Identity by name

A workspace Coworld has its name as its identityQ1, and the registry row, folder and record store use the name as their key. The current version is a field: version id, version string, source commit, previous version and time of change. Every platform call that needs a version (upload, evaluate, XP requests, submit) uses this current id, never a cached one.

A migration gives current workspaces the new folder name and re-keys the registry row and Sessions. The coworld field in MIXIN.md names the Coworld by name, and its mismatch check stops the comparison to the version id29.

B2 · Switch

workspace.coworld_switch takes a Coworld name, or a version id that it resolves to its name. It always lands on the canonical version.

B3 · Follow

A watcher step reads the canonical version for the active Coworld's name, one read on each 10-minute champion-sync intervalQ7. The platform client has find_canonical_coworld(name), so metta needs no change. A different canonical version starts the upgradeQ2.

B4 · The upgrade in code

The new function coworld_setup.upgrade(name, new_version_id) does the six steps in Figure 2, with no model. It moves the read-only source checkout to the new commit and never overwrites code/ (the agent's repository and mixin). It fast-forwards code/mixin/ only when the workspace never edited it, and otherwise it puts the mixin diff in the event payloadQ3. Appendix A gives each step.

Records, Tasks, Versions, worktrees and documents stay where they are. Researchers in progress continue, and their subsequent platform calls use the new version idQ2.

B5 · The upgrade wake

The upgrade wake is a new wake kind for coworld.version_changed. Its prompt gives the manifest diff, the source changes between the two commits and the mixin diff. The agent updates an edited code/mixin/ if the source mixin changed, then rebuilds and evaluates the champion on the new version. If the policy breaks, the agent opens a Task to repair it and resubmits only thenQ4. Last, ui.notify tells the user what changed and what the agent did.

The wake starts only after the version stays the same for a quiet periodQ6. Thus several quick versions start one wake for the latest, which matters for spend.

B6 · Results across versions

Each experiment run and Version records its Coworld version. The stats code flags comparisons that mix versions, because a result from 0.6.3 can be false on 0.7.3.

B7 · Champion sync after B1 to B3

Champion sync matches leagues by name and expects the workspace's version. A difference that lasts past one check interval means a league locked to an older version, which is normal and rareQ5, or a failed upgrade, which is a Part C alarm.

5 · Part C: tell the Orchestrator when an invariant breaks
  • The code bugs from Table 1 get direct repairs.
  • A break from outside raises a persisted, deduplicated alarm: a wake when the agent can act, otherwise a user notice.

C1 · Repair the code bugs

Cases #1, #3, #7, #9, #11 and the malformed-wait half of #6 get code repairs, not alarms. Appendix A lists each repair.

C2 · Watcher alarms

A step that finds a broken invariant from outside raises an alarm: a persisted condition with the key (step, condition, subject). The first time that the condition holds, the step emits watcher.alarm, which starts one management wake and adds a briefing line. It stays quiet while the condition holds and arms again when it clears. The current stuck: and schema_newer: markers, which a meta value guards, have the same shape1828. The same step error on N consecutive ticks also becomes an alarm, and ctx.notes goes away or feeds alarms.

C3 · Wake or notice

ResultCases from Table 1
Wake (the agent can act)#4: no league for the Coworld's name, or a failed upgrade (B7). #5: a merge held on a dirty main. #6: a Task that waits on a failed dependency (the Orchestrator plans again or abandons it). #8: checks that fail in the worktree or git step. Any step error repeated N ticks.
User notice only (the agent cannot be woken or cannot act)#2: runs API down. #10: context build failed. For these two, the tick also exits non-zero, so Hermes raises its own cron failure notice. #12 already gives a notice.

C4 · Wake machinery

New wakes use the current wake machinery, so the JAME-176 loop guard, batching, and the follow-up task that stops one wake.failed for each event of a failed batch all apply.

6 · Order, validation and risks
  • Part A first, then the C1 repairs, the alarms, and Part B in two steps. The largest risk is a migration error.

Order

  1. Part A in #153 (in progress).
  2. C1 code-bug repairs, as a small, independent PR.
  3. C2 and C3, the watcher alarms.
  4. B1 and B2, identity by name, with the migration.
  5. B3 to B6, follow and upgrade.

B can start before C. C2 gives a failed upgrade its alarm.

Validation

Fake platform, migration, regression and alarm tests, plus a cost-capped model run of the upgrade wake before release, prove the plan (Appendix A).

Risks

Risk · migration The migration touches every store row that names a Coworld, and an error strands recordsQ1. Mitigation: test the migration on a real workspace copy, and keep the old folder until the new one passes the doctor.
  • Upgrade wakes cost money. Seven Generals versions in about 26 hours would be seven wakes with no debounce. Mitigation: the debounce, plus the inference gate (JAME-174).
  • A version change in mid-experiment mixes results. Mitigation: B6.
  • The automatic mixin fast-forward can overwrite a workspace edit if the "never edited" check is wrong. Mitigation: compare against the recorded import commit, and when in doubt, never fast-forward.

7 · Alternatives considered
  • Keep the pin. It drifts within hours, and id comparisons break.
  • Move with today's coworld_switch. Each move makes an empty Coworld and a full setup wake.
  • Let the agent look for new versions. Polling in the model context, which another task removes.
  • A platform push event for new canonical versions. Not necessary: one read each 10 minutes is cheap.
  • An upgrade all in code, with no wake. Code cannot judge whether a policy still works or merge an edited mixin.
  • Keep the first version id as the stable key, with the current version beside it. No folder migration, but the key names a version that the workspace does not run. This is the alternative in Q1Q1.
  • Make every broken invariant a wake. Some breaks (runs API down) cannot wake anyone, and noisy alarms repeat the Nov 2 storm. Thus alarms are deduplicated and split into wakes and notices.

Appendix A · Implementation detail

A.1 · How a switch works today

The switch registers the id and makes the folder and code repository. For a new Coworld, it calls fetch and emits coworld.setup_needed8. fetch clones the source one time at the manifest commit, copies the mixin (a folder of files from the Coworld source) into code/mixin/, and imports seed claims and lessons9. The setup wake is agent work on top of that: make the mixin usable, import lessons, do capability checks, make the starter policy and upload it10. The setup wake does not fetch the source. The code in the switch does that.

A.2 · The upgrade steps (B4)

coworld_setup.upgrade(name, new_version_id) does these steps:

  1. Read the manifest of the new version (source URL and commit).
  2. Move the source checkout, a read-only reference copy, to the new commit (git fetch and checkout).
  3. Never overwrite code/ (the agent's repository and mixin). If the workspace did not edit its mixin after the import, fast-forward code/mixin/ to the new source's mixin. Otherwise, leave it, and put the source mixin diff in the event payload.
  4. Import the seed files that are new in the new commit. The import is plain code: it parses the Coworld's seed/ folders and skips a summary that is already in the store. Re-running it is not enough on its own. An edited lesson has a new summary, so it would become a second claim, and a deleted lesson would stay. So the step compares the seed files of the two commits and lists the changed and removed ones in the event payload. The upgrade wake then supersedes or retires their claims.
  5. Record the change in the registry, and emit coworld.version_changed with the old and new versions, commits, a manifest diff (player runtime, variants, commands) and the mixin diff summary.
  6. Mark the capability checks due. On its next tick the watcher runs the mixin's build, check and evaluate commands and a dry-run upload. That is a smoke test: it shows the policy still builds and uploads. It does not show the policy still plays well on the new version, because evaluate only scores results that exist. The upgrade wake runs the champion on the new version for that.

A.3 · Code-bug repairs (C1)

  • #1: Do not acknowledge an event whose handler deferred.
  • #3: Count busy and unavailable starts toward give-up after a time limit.
  • #7: Run anti-stall in its own step, isolated from goal conditions. Validate anti_stall.hour when it is set.
  • #9: Put a limit on no-model handler retries, then raise wake.failed.
  • #11: Page events.unhandled past the events that the watcher gave up on.
  • #6: Refuse a malformed wait at the call to task.wait (an empty ref, an unknown kind, a malformed user ref).

A.4 · Tests

  • Fake platform tests: a new canonical version in mid-research upgrades in place and keeps records and Tasks. It emits one coworld.version_changed, and several quick versions start one debounced wake. The source moves to the new commit. An unedited mixin fast-forwards, and an edited one stays, with a diff in the payload.
  • Migration test: a store keyed by version id migrates to name keys, with records and Sessions intact.
  • Champion sync: different versions of one Coworld still join, and no league by name raises one alarm.
  • Each C1 bug gets a regression test. Each C3 alarm gets a test that it fires one time and arms again after it clears.
  • Before release, a cost-capped model run of the upgrade wake on a real Coworld version change.

Appendix B · Decision Record
D1 · Settled

The canonical version is always the target. Lost: "the version that the leagues run." The two are different only for a locked league.

D2 · Settled

A version change is a notification to review the changes, never a wipe. Lost: a switch that makes a new Coworld.

D3 · Answered question

Old policies continue to operate on the platform after a version change, and they can break. The agent must check its policies on the new version. Answer: they still count.

D4 · Answered question

The harness (the ide-distributions watcher) owns wakes and version follow, not the client. Answer: the pin is in ide-distributions, and the IDE in metta never switches Coworlds.

D5 · Settled

A difference between the workspace version and the league version must be very rare. When it stays, it is a fault to report.

D6 · Settled

Part A ships in #153 as a stopgap.
