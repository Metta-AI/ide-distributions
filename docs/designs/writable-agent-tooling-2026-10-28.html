Design · 2026-10-28 · Proposed

Writable Agent Tooling in Hosted Hermes Workspaces

Tooling that hosted agents can change, keep across releases, and run.

Executive Summary

Hosted research agents (the orchestrator and the researchers) cannot change their tools. Most of their code is links into the read-only image, and Hermes (the agent runtime) recopies skills and SOUL.md at each release. Thus an agent fix fails or disappears.

In this design, each profile folder is a git working tree on the workspace disk. Releases merge into the agent's main, and a conflict keeps the agent's version. Plugins fall back to the image copy when the writable copy fails. The GitHub tools go away. The main tradeoff: the design reverses a metta hosting rule, and agents can break their own tools.

1 · Problem
  • Hosted agents cannot write their code, game folders or plugins, which are read-only image links.
  • Each release erases agent edits to skills and SOUL.md.
  • Goals: writable tooling that survives releases, and no agent use of Softmax's GitHub connection.

On a hosted workspace, each profile folder (/opt/data/profiles/<name>, the home of one Hermes agent) holds links into the read-only image for src, scripts, games, doctrine, docs, tests, pyproject.toml, uv.lock and the shipped plugins12. Metta's prepare_code replaces those paths with symlinks on every start3. The hosting contract states that "installed game source stays read-only and byte-identical to the pinned distribution"4. Only GotA's generated tools/.cache and tools/bin in the researcher are bind-mounted writable5. The orchestrator's GotA copy has none, so orchestrator GotA builds fail.

Skills and SOUL.md (the agent's standing instructions) are writable copies. But Hermes's distribution updater deletes and recopies every distribution-owned path on each update6. Hosting declares skills and SOUL.md distribution-owned7. Thus skill edits disappear at the next release.

This week, a read-only cache in Pudge replay_inspect blocked three cards for about 2.5 hours. ide-distributions #73 reverted the GotA build relocation from #71. Doctrine 16 (an agent rule) tells agents to copy a broken game folder to disk and run the copy, which is a workaround, not a fix.

The goal: everything an agent uses to work on policies, reply to the user and use Softmax is writable by that agent, survives releases, and runs from the writable copy. This covers game folders (GAME.md, tools, game skills, guides), generic tools (the research CLI, ide_research_core, the orchestrator and researcher plugins), scripts, skills, SOUL, doctrine and knowledge.

The second goal is to remove github_clone and github_repositories. Agents must not use Softmax's GitHub connection.

2 · Design
  • Each profile folder is a git clone of a per-distribution repository on disk.
  • Releases merge into the agent's main, and conflicts keep the agent's version.
  • Code runs from the profile copy, with an image fallback.
  • Agents use plain git clone, not the GitHub tools.

2.1 · Tooling as git working trees

Metta keeps one bare repository per distribution on the workspace volume: /opt/data/tooling-orchestrator.git and /opt/data/tooling-researcher.git. Metta commits each release onto a release branch there. The tree is the image's distribution folder, the parent is the previous release commit, and the message names the source commit.

Each profile folder is a clone of its distribution's repository, with main checked out. The paths that are image links today, plus plugins/*, skills/ and SOUL.md, become ordinary tracked files.

The profile root does not move, so no lookup changes. The game loader's DISTRIBUTION_ROOT8 and the plugin entry's <profile>/src9 already resolve inside the profile. An agent edit is a file edit plus a commit.

Researchers share edits by a push of main to the shared repository, which each researcher merges. The orchestrator has its own repository (different SOUL and plugin)Q2.

2.2 · Releases merge into agent edits

At start, preparation commits the image tree onto release. Then it merges release into the profile's main. On a conflict, preparation aborts the merge, keeps the agent's version, and records a notice that status reports: "tooling update deferred; merge release yourself"Q3. publish_game_doctrine already applies the same rule to doctrine in game repositories10.

Untracked files, such as agent-added skills, are never deleted. Hermes's own updater stops ownership of skills and SOUL.md. The hosted manifest projection lists only config.yaml, cron and distribution.yaml as distribution-owned7.

On an existing workspace, the first adoption replaces the image links with a checkout of the first release commit. Those paths were read-only, so no agent edits exist to keep.

2.3 · Code runs from the writable copy, with a fallback

Plugin entries import from <profile>/src, as today. If that import fails, the entry loads the image copy (/opt/ide-distributions/<distribution>/src) and records the error for status and the agent. Without it, one bad edit kills the agent's tools with no way to repair them. The PyYAML import fixed in ide-distributions #90 did exactly that to status.

The research CLI runs the profile's src first. The image venv's editable install points at the image path11, so the launcher puts <profile>/src first on the import path.

The image venv (/opt/ide-venvs/<distribution>) stays the default source of dependencies. An agent that changes pyproject.toml builds its own venv on disk with uv sync. The launcher prefers <profile>/local/venv-agent when it exists and matches uv.lock.

Game builds write inside the game folder (tools/.cache, tools/bin), which is now writable. As a result, the GotA image volumes5 go away. Build receipts and provenance checks key on the tools folder's git tree hash, not byte-identity with the image4. The researcher guard plugin and the episode budget ledger become editable tooQ1.

2.4 · Removing the GitHub tools

The change deletes the orchestrator's GitHub module (github.py) and the github_repositories and github_clone registrations12. It also deletes their README rows and the SOUL "Repository review" text, which requires those tools and the repositories/ folder13.

The new SOUL text says: clone public repositories with git clone into any writable folder. Private repositories are not available. research source fetch14 stays as an optional helper for pinned, cached snapshots. game-create and coworld-context use it, but nothing requires itQ4.

2.5 · Instructions

SOUL, KNOWLEDGE and doctrine say: your tools, skills and game folders are yours to read, fix, extend and build. Commit changes with a message that says why. Researchers push useful changes. In Doctrine 16, "fix the tool in place and commit" replaces "copy the game folder to disk and run the copy".

4 · Rollout and Validation
  • Safe ide-distributions changes first, then metta, then instructions.
  1. ide-distributions: remove the GitHub tools (independent, ships first).
  2. ide-distributions: plugin import fallback and launcher src-first (harmless while paths are still links).
  3. metta: tooling repositories, release merge, layout change, GotA provenance, image-volume removal. The existing Hermes release qualification (a canary chat before and after restart) qualifies it.
  4. ide-distributions: instruction updates once step 3 is live.

Validation: release qualification passes. On a canary, edit a game tool and a skill, commit, restart and release a new image, and make sure that the edits survive and merge. Break src on purpose and make sure that the fallback loads and status reports it. Build GotA from the orchestrator.

5 · Risks
  • Main risks: a reversed hosting rule, broken tools, and old tooling after a conflict.
Risk The change reverses an explicit metta hosting rule4 that Rohit owns. Agree on it with him first.
  • An agent can break its own tools. The fallback and git revert limit the damage.
  • A release conflict leaves a profile on old tooling until the agent merges. status must show this.
  • Tooling history uses disk, but little next to game caches.

6 · Alternatives Considered
  • Each alternative loses edits, solves only part, or keeps GitHub access.
  • Copy the tooling to disk at each start, without git. Releases overwrite agent edits, as Hermes does to skills today, or never update them. No history, review or revert.
  • Put game folders in each game's canonical research repository. This ties game tooling to research card integration, leaves generic tooling unsolved, and gives two mechanisms instead of one.
  • Relocate caches per game (ide-distributions #71). This repairs builds only, one game at a time. #73 reverted it for that reason.
  • Keep github_clone behind a git credential helper. Agents still go through Softmax's GitHub connection, which is not allowed.

7 · Open Questions

  1. Should guardrail code stay read-only?

    Context The researcher guard plugin and the episode budget ledger become editable. The config.yaml deny lists are already writable.

    Options (a) Everything is writable, and only server-side limits bind (credential scope, spending caps). (b) Keep plugins/researcher_guard and the budget code image-owned and read-only.

    Recommendation (a), consistent with the "act without asking" direction.

    Raised in §2.3 Code runs from the writable copy, §3 Who Changes What

  2. Share edits across distributions?

    Context Researcher and orchestrator ship separate copies of each game folder, so a researcher's game-tool fix does not reach the orchestrator.

    Options (a) Separate repositories, shared by hand. (b) One host repository with the whole ide-distributions tree, each profile a sparse checkout of its folder.

    Recommendation (a) now, and (b) later if divergence becomes a problem.

    Raised in §2.1 Tooling as git working trees

  3. Should agent improvements flow back upstream to ide-distributions?

    Context Nothing sends agent edits back to the source repository.

    Options (a) No. (b) A periodic export of tooling diffs for human review.

    Recommendation (b), as a follow-up.

    Raised in §2.2 Releases merge into agent edits

  4. Remove the IDEa GitHub setting and broker endpoints?

    Context The IDEa "Connect GitHub repositories" setting (coplay #9) and the Softmax GitHub broker endpoints lose their agent use.

    Options (a) Remove them. (b) Keep them for other clients.

    Recommendation Ask the coplay and metta owners. Out of scope here.

    Raised in §2.4 Removing the GitHub tools

Appendix A · Decision Record
D1 · Settled

Tooling lives in git: one bare repository per distribution, and the profile folder is the working tree. Lost: a plain copy, and per-game relocation. Why: releases must merge with edits, and git gives history and revert.

D2 · Settled

Release conflicts keep the agent's version and defer the update with a notice. Lost: the release wins. Why: this matches doctrine handling and never discards agent work.

D3 · Settled

The GitHub tools go away, and agents have no Softmax GitHub access. Lost: a credential helper. Why: agents must not use the connection.

D4 · Settled

A failed plugin import falls back to the image copy. Lost: no fallback. Why: a broken edit must not leave the agent without tools.

D5 · Settled

research source fetch stays optional. Lost: removal. Why: it gives pinned, cached snapshots and does not use the GitHub connection.
