IDE Profile Refactor

Owner: James Boggs. This design expands James's partial draft1 into a full design for the Orchestrator and Researcher profiles. We checked it against ide-distributions main, metta, Hermes v0.21.6 (the agent runtime) and playerADE (an earlier agent harness that we use as a reference). Metta is the main Softmax repository. It holds the Softmax IDE (the web app where users work with the agents) and the bridge (the hosted service that connects clients to Hermes). We also used a review of the problems in the current profiles190. Where they conflict, this design supersedes two earlier designs: the multi-game design2, which ran several games in one profile, and the Orchestrator design of 2026-10-153.

1 · Summary

This design rebuilds the Orchestrator and Researcher profiles of ide-distributions (this repository) for Hermes v0.21.6. A profile is one agent configuration: its SOUL.md system prompt, tools, skills (instruction files that the agent loads on demand) and config. Users write policies (programs that play a Softmax game, a Coworld) and enter them in leagues. Three principles lead the design. The user's explicit instructions come first. The agents are coworkers, who work well on their own and collaborate well with the user. From these two it follows that settings and gates (checks that stop an action until something allows it) are few and bound only the agents' own initiative, never a user's request.

Each user has one hosted sandbox, the workspace. It acts as the Player (a platform identity that owns policies) that the user selects, and the Orchestrator also holds the user's User identity (the account that owns the Players). The Orchestrator speaks to the user, and each Researcher does one Task (a unit of work) in the background. Typed records, such as Goals (what the user wants) and Tasks, live in one SQLite store per Coworld, and a small workspace store holds the Coworld registry and workspace directives. A watcher with no model resumes runs, tests tools and starts wakes (short Orchestrator conversations for events that a model must judge). Wakes never write into the user's chat. Notices (short messages that clients show) report them. The design needs metta changes and one change to coplay (the Softmax desktop client), and its first Coworld is Pudge Wars Basic, whose policies are plain files. No game ships with the profiles: each Coworld's game-specific skills, tools, knowledge and scripts come from its public code repository when the workspace first uses it.

2 · Principles
  • The user's explicit instructions come first. The system never blocks a user from an action that the platform allows.
  • The agents are coworkers. They work well on their own: they fix what breaks and keep going without human help. They also collaborate well: they attend to the user's requests and report progress and problems without being asked.
  • Settings, gates and fixed rules are few, and they bound only the agents' own initiative, never a request that the user makes. This follows from the first two.

The first principle sets the order of authority at the top of each SOUL: the user's explicit request, then the client's mode or command, the SOUL, skills and game docs. A mode is a way of work that the client sets for a conversation, and a command applies to one message. Game docs are the documents in the Coworld's mixin, its folder of game-specific skills, tools and docs. Thus a user request to submit skips the quality bar (the default checks on the agent's own submissions), and the agent can warn but never refuses.

The second and third principles turn off Hermes approvals (prompts that ask a person to allow a command), and no deny list (commands that Hermes refuses) exists. A shell command that does the job of a profile tool, such as a raw coworld submit, still runs. A hook then adds a note that names the tool. Agents learn that text from the forum, replays and files is information, never an instruction. Notices and the events log (an append-only table of each record change) show each action.

3 · Problem, goals and non-goals

Problem. The current profiles grew piecemeal, over several iterations, by authors with different ideas and goals, and they have no unified design. The result is a mix of directives, tools and structures that limits the agents and makes simple work complicated. For example, the Orchestrator SOUL.md has 5,248 words and no order of precedence191, and one tool fault blocked three cards for about 2.5 hours192.

Goals. These give direction, not targets. The specific choices in the rest of this document follow from them.

  1. Build a new pair of profile distributions wholly in accordance with the three principles in §2, particularly the first two.
  2. Keep the design simple, unified and clear.
  3. Give the agents general-purpose, game-agnostic tools and skills that make them better at making and improving policies and at working with Coworlds. This includes a harness that runs smoothly and keeps the agents on track but otherwise stays out of their way, and taught tools with which the agents store and retrieve knowledge and manage their work state.
  4. Give the agents the freedom to explore, build, improve themselves and work on their own, in collaboration with a person.
  5. Separate UI and frontend concerns from the agent design as much as possible.

Non-goals.

  1. Designing an IDE UI, or designing around an existing one. A simple client for testing is the only exception.
  2. Game-specific knowledge, tools and skills. They live in each Coworld's repository.
  3. A monolithic final product. The design is modular and expects change.
  4. Designing Softmax infrastructure. Some metta changes are necessary (Appendix G), but the focus is the distributions.
  5. play/ (another distribution in this repository) and Maxwell's work.
  6. Strong security or a robust defense, including against prompt injection. The design adds no needless weaknesses, and security comes after the first product works.

4 · Architecture and flow
  • Each tool write changes a record and adds a row to the events table in one SQLite transaction. The bridge reads that table to update clients.
  • The watcher has no model. It resolves waits, checks tools, merges reviewed work into main, and starts, steers (sends a message into), stops and resumes runs.
  • Clients are not authoritative. Any number and kind of client can attach if it obeys the published contract.
  • Clients: the Softmax IDE, Coworld sites (web pages that a Coworld provides) and coplay.
  • Bridge: a sidecar (a helper service beside Hermes in each hosted workspace) in metta's observatory-hosted-worker package. It does only transport: authentication, run requests and the event stream.
  • Hermes: Orchestrator chat and wake Sessions, and Researcher Task Sessions. A Session is one Hermes conversation, and a run is one execution of it through the Hermes runs API.
  • Profile plugin: record and platform tools, the ui tool (it shows records and panels in clients and sends notices) and an advisory hook. It adds two prompt sections: the briefing (a computed status summary) and the session context (what the client declared at session start, such as its mode).
  • Code repository (code/, git): the policy, the Coworld's mixin and one worktree (a separate checkout) per Task.
  • Watcher and dispatcher: a Hermes no_agent cron job of the Orchestrator profile (a scheduled script with no model) that starts each minute. It works like the supervisor job of the current profiles4, which polls XP requests, credits and permits.
  • Softmax platform: uploads, XP requests (paid evaluation episodes), submissions, leagues, forum and wiki.

A tool call appears as tool.action: each record kind has one tool, and an action field selects the operation, as in task.complete. The tool count matters. Hermes defers tools behind a search step (tool_search) when a profile has many107. A budget of about 25 tools per profile, with a target of 15–18, keeps all of them loaded.

5 · The records
  • Records are SQLite rows with integer ids and a type prefix, such as G-3 or T-42.
  • A Task has one of four types (research, improvement, ideation, maintenance). A Task that a Researcher suggests stays proposed until the Orchestrator or the user accepts it.
  • A Version is a policy candidate that an agent makes on purpose with version.create. That step is separate from the merge of a Task's branch into main.
  • The Goal and Task records are the plan, so agents keep no plan file.

Constraints and triggers keep each record valid. The store library marks each of its writes, and the watcher reports unmarked writes, such as a direct sqlite3 edit. A Session holds its Task by a lease, a hold that it renews while it works and that the watcher clears when stale. Appendix B lists the fields.

  • Goal: what the user wants, with an end state and a status. If 3 ideation Tasks (which propose new Tasks) bring no progress, a wake parks the Goal (puts it on hold).
  • Task: one unit of work under a Goal, with dependencies, a waiting_on field (what it waits for) and a type checklist (the deliverables that its type requires). A failed Task records what failed and a next step.
  • Version: a commit of policy code, or a policy that the user uploaded elsewhere.
  • Champion record: the policy version that currently represents the Player in a league, which is not the league's winner.
  • Claim: a short finding with typed evidence links (to code, replays, measurements and other kinds). Each read computes its freshness, whether its evidence is still current.
  • Experiment: a comparison of Versions whose method locks at start. The current decision-rule code5 gives confirmed, refuted or inconclusive.
  • Directive: a standing user instruction, on the workspace or on a Goal.
  • Coworld registry: one row per Coworld with its platform id, folder, mixin version and tool-check status (whether its commands passed their last test). The registry and workspace directives live in a small workspace store.

6 · Identity, storage and the active Coworld
  • Each user has one IDE sandbox139. At creation, the user selects which Player the workspace acts as, and both profiles use that Player's credential.
  • The Orchestrator also holds the User identity. It always reads with it, and it writes with it when the write serves the user's requests or Goals, with a notice and an events row for each write.
  • The sandbox has one folder per Coworld with code, worktrees, documents and a store. The watcher, the tools and the briefing see only the active Coworld.
  • The profile machinery (the store library, the watcher, and the plugin's record and platform tool code) is fixed and read-only. All else that the agents use is writable, and the agents fix it.

The writable part covers game code, mixins, optimizer code (the per-Coworld policy-improvement code and tools), game tools, caches and skills. When the machinery breaks, the Tasks that need it wait and the user gets a notice.

The platform Coworld id is the only stored identifier of a Coworld, and folder names come from it. A user request to work on another Coworld starts workspace.coworld_switch at once, which drains active work (stops it and marks it to resume). Hermes then loads the new mixin's skills, whose names start with the Coworld name.

prepare.py, the profile's setup script, runs after each install and each profile update. It makes the store, applies migrations and removes retired config (settings that the profiles no longer use).

7 · Roles
  • The Orchestrator speaks to the user and manages the work. Only the Orchestrator submits, switches the Coworld, uses the ui tool and holds the User identity.
  • A Researcher does one Task per Session in the background, speaks only to the Orchestrator through its Task, and proposes Tasks and submissions.
  • Both profiles make Versions, upload policies, request XP and repair broken tools, with no limit on turns or run time.

Appendix C.5 compares the two roles.

8 · Execution, wakes and repair
  • A Session that must wait sets waiting_on and ends its run. The watcher resumes the same Session when the wait resolves.
  • The watcher follows only what a Task waits on, plus champion changes, and tools read all else live.
  • Each event that a model must judge gets its own short wake Session. Each event kind has exactly one handler, and a test checks this.
  • A broken tool creates one high-priority maintenance Task, and only the Tasks that need that tool wait for the repair.

Hermes Kanban cannot resume a Session or steer a live worker108109, but the Hermes runs API can110111. Thus the watcher itself starts a run for each accepted (unclaimed) Task while fewer than max_researchers runs (default 2) are active. Spike S1, a test before the build, checks that several runs in one profile stay isolated. If they do not, Kanban becomes the Task table.

task.complete checks that the deliverables of the Task's type exist and names any that are absent. A review wake (a short Orchestrator Session) then judges the substance, and it can reopen the Task so that the same Session resumes with feedback. The watcher merges accepted work with no model, after the mixin's build and check commands pass again.

The setup wake prepares a Coworld when the workspace first uses it. It clones the Coworld's public code repository, at the commit that the release pins, into source/ in the Coworld's folder. That repository holds all game-specific material: the mixin, skills, tools, knowledge and scripts. Its layout differs between Coworlds, so the wake finds the mixin and copies it to mixin/ in the policy repository, where tools look for it. If there is no mixin, the wake builds one with mixin-from-scratch. It imports all of the repository's lesson notes as claims180, in whatever format they use. Setup ends only after the Coworld's starter policy (the example policy in its repository) builds and one upload, real or dry-run (a test of the upload route), passes.

Tool checks are real runs of each mixin command, in the setup wake, at each release and each day. A failure marks that capability unavailable and creates one maintenance Task, which takes the next free Researcher slot.

9 · Memory, briefing and notices
  • Hermes built-in memory is off. A standing user instruction becomes a directive record, which the briefing shows, so compaction (when Hermes shortens a long conversation) cannot lose it.
  • A computed briefing goes into each Session's system prompt and renders again after compaction.
  • Wakes never write into a conversation. ui.notify is the only channel for background news, and unread notices open the next chat turn's context.

The briefing is a Hermes prompt section112 of up to 4,000 characters. It holds the workspace status, the results of the capability check (which logins, CLIs and build routes work at session start), the champion, the Session's Task, the active Goals and the directives.

10 · The client contract and the agent context panel
  • The profiles own one small contract with an integer contract_version, published as JSON Schema files in this repository.
  • The contract has three channels: context into each run, ui tool output, and one event stream per workspace that keeps all clients in sync.
  • The bridge builds the Hermes request, passes only contract fields, and drops free instruction text from clients.
  • An agent-context panel shows what the agent sees and what it needs from the user. Each client decides how to present it.
  • The rest of the design needs only a small seam from this section. Everything else here is a separate layer that ships later, after its own design and in its own stack.

The seam. The rest of the design needs two things from clients. First, each turn carries the user's message and one typed context block, and the bridge stamps it with the sending client, the active Coworld, a "changed since your last turn" note and the unread notices. Second, notices reach the user: the store writes them as events rows, and clients show them. The store, the watcher, wakes, records and submission depend on nothing more. The client stamp selects the client guide, and without ui.ask the agent asks in chat.

The contract layer. Everything else in this section and in Appendix A ships after the rest of the design: the versioned JSON Schema files, session-open and capabilities, the ui panels and UI state document, sync between clients, and the agent context panel.

A client sends session-open once, with its identity, a session context and its capabilities: the views and panel kinds (content types such as Markdown or replay) that it can show. Each turn sends {message, context}, and the bridge adds the validated context to the request as one labeled JSON block.

The ui tool changes the UI state document (the store record of what the agent shows) and never waits on a browser. A user's answer in the UI, such as an answer to ui.ask, reaches the Session at once: it goes into the running run, or it starts one. A reaction (an emoji or a thumbs up or down on a message) is feedback that the agent sees at its next turn, and it never starts a run. Hermes plugins cannot serve HTTP113, so the bridge serves the events rows as one SSE stream (Server-Sent Events). Clients do not poll: each keeps one HTTP connection open, and the bridge pushes each new row as it appears in the store. A client that reconnects asks for the rows after the last one it saw.

The watcher computes the agent-context panel from records, the session context and tool checks, with no model. It shows the active Coworld, the acting Player, Goals, the champion, recent Versions, running Tasks, broken capabilities, and what the client sent with the last message. The agent writes only the "I need from you" items, which only the user can supply.

11 · Submission and the platform
  • A user request to submit runs at once: the Orchestrator makes a Version, uploads it and submits it in the same turn, and cites the user's message.
  • An autonomous submission (one on the agent's own initiative) must pass a default quality bar: a merged Version and a confirmed Experiment against the champion. With no champion, a merged Version that passes the mixin's checks is enough.
  • Upload takes any Version, and submit takes any uploaded Version.
  • Each Version shows one submission status, computed from platform states: uploaded, submitted, qualifying, competing or champion.

With submissions.mode set to ask, the Orchestrator asks before each autonomous submission. Each one sends a notice, and a pause (the user's paused setting) stops them with all other background work. Upload sends the exact built bytes and checks the hash. A policy that the user uploaded elsewhere becomes an adopted Version193.

12 · Mixins, skills and instructions
  • No game ships with the profiles. A Coworld's public code repository holds all its game-specific material, and its mixin is the folder that the tools use. The mixin's place in the repository differs between Coworlds, so the setup wake copies it to mixin/ in the workspace. It holds a reference policy, a build script, docs, a lab AGENTS.md (the game's rules and scoring) and five binding skills, which the shared core skills call for game-specific steps.
  • Each SOUL is short and starts with the order of authority. Guidance that changes lives in skills, which an agent reads at each use, so updates reach open conversations.
  • The prompt text (SOUL and doctrine) is generated per role from shared parts at build time. CI checks word counts and contradictions, and a failure blocks the release.
  • The shared Python code becomes one package that uv installs into both profiles, so no code is copied.

The MIXIN.md front matter holds the fields that tools read: the commands (with evaluate) and metrics, the Coworld id, the artifact kind (a file or an image) and the toolchains (other runtimes, such as Nim). The agents can edit the front matter and the commands, as they can edit the rest of the mixin. Tools read player_runtime (file or container policy) only from the Coworld manifest. When a local copy disagrees, the agent fetches the platform's manifest for that Coworld version through the Softmax API. Mixin skill names carry the Coworld name.

13 · Rollout and validation
  • There is no migration: we erase the current workspaces after a notice to users, and the profiles install fresh.
  • The profile work is a seven-entry Graphite stack (a series of dependent pull requests). Metta has its own stack, coplay has one change, and all three ship together.
  • A release ships only if "submit the starter as my champion" on a new workspace ends in a submission. The test runs on the fake platform (a test double of the Softmax platform) and on the release canary (a hosted workspace that gets each release first).

The stack adds, in order: the shared code package, the store library, the record tools, the watcher, Versions and submission, the client seam, and the skills and SOUL. The contract layer (§10) follows in its own stack. Each entry deletes the old code that it replaces (Appendix F.1). Appendix G lists the metta and coplay changes.

hermes profile update keeps the old config.yaml6, and today's prepare.py only adds config values7. Thus releases reinstall the profiles, and the new prepare.py also removes retired config. The Asana ticket that asked metta to roll out the build inbox (a hosted route for policy image builds) is closed, because Rohit's rework replaces the inbox.

14 · Risks

  • With few gates, an agent can act on an injected instruction (R10) or run a harmful command (R11).

15 · Alternatives considered
  • The design uses its own contract, not AG-UI, A2UI or MCP Apps, the public protocols between agents and user interfaces. None of them fits one stream that several clients share10.
  • It uses its own dispatcher, not Kanban, because Kanban cannot resume a Session. It uses SQLite, not files in git, because a database keeps related records consistent.
  • It uses teaching and visibility, not approvals and deny lists, because approval prompts stopped unattended work194.

Appendix A · Client contract reference

Most of this appendix is the contract layer (§10), which ships after the rest of the design.

A.1 What exists today

  • The IDE's Next.js server builds the full native Hermes body with instructions157, and then freezes it158. The bridge forwards it unchanged and fingerprints it for idempotency141. The workspace context is free-form, with no schema or version159. The Orchestrator SOUL only says "read the IDE context each turn"11.
  • With pull request #70, the Orchestrator reads one typed block from instructions: Coworld repository context v1: followed by JSON with the league, game, Coworld and pinned source_url. It validates the block, fetches COWORLD.md from that source, and gives it to the model on every request12. coplay already sends this block160. The design removes the per-turn selection and keeps the fetch for the setup wake.
  • The IDE MCP server has one tool, ide_workspace161, reached by a hand-written JSON-RPC client13. It is removed, not extended.
  • The contract uses these Hermes hooks. register_system_prompt_section(id, content|callable) is frozen per session and re-rendered after compaction, with a limit of 4,000 characters per section and 8,000 in total112. pre_llm_call can add text to a turn's user message115. register_middleware("llm_request", …) changes each model request payload, but it does not change the cached system prompt or the history116. Plugins cannot register HTTP routes113.

A.2 Contract files

The contract files are contract/context.schema.json, contract/ui-state.schema.json, contract/events.schema.json and contract/capabilities.json, plus a short human-readable spec. contract_version is an integer. CI checks the generated copies. The bridge reads the schema from the installed profile through a read-only CLI command (research context-schema). The reason is that kept workspaces keep their pinned image, and metta pins ide-distributions by commit142.

A.7 Rules and limits

  • Only contract_version is required.
  • Turn context total ~16 KB. client_data ~8 KB. on_screen[] ~20 items. Large items travel as references the agent fetches.
  • mode and command: name ~40 characters, instruction ~1,000 characters. Oversize values are refused with a clear error, never truncated. No mode means default behaviour. Mode is guidance with strong authority: it directs the conversation and outranks the agent's judgement on how to handle requests. Only the user's explicit request outranks it. Settings and profile rules bound the agent's own initiative, never the user's explicit request. The backend does not enforce modes.
  • Validation: each client validates its own user input. The backend validates incoming context at its boundary, drops unknown fields, refuses malformed fields with a clear error, and never crashes a turn on a bad block.
  • The bridge may omit, truncate or format any field it passes on, and it passes only contract fields.
  • Session context is set at session-open by the first client and changes only through session-update. The change is recorded and a pre_llm_call hook (or the llm_request middleware) tells the model.
  • Prompt sections: briefing ≤ 4,000 characters. Session context and attached-client capabilities ≤ 4,000 characters (Orchestrator only).
  • Event stream: bridge tails events about every 0.5 s. Non-chat updates can be up to ~0.5 s late.

A.11 Event stream

  • The events columns are seq (integer primary key), at, actor, kind, subject and payload (JSON). UI-state changes carry a JSON Patch (RFC 6902).
  • GET stream?after=<seq> serves SSE to every attached client: one open connection each, with new rows pushed as the bridge sees them, and no client polling. snapshot returns the current records and UI state with their seq. A messages read returns final messages from the Hermes transcript.
  • Live chat tokens are relayed from the Hermes run stream to the clients attached to that conversation.
  • Clients ignore event types and content kinds they do not know.
  • Locally, research serve offers session-open, message, ui-action and stream endpoints against a local Hermes.

A.13 Agent context panel

A fixed-name panel agent-context in the UI state, built from the existing panel kinds and streamed like any panel. It answers the user's question of what the agent sees195.

  • Workspace part: the active Coworld. The acting Player and whether the User identity is available. Goals and the champion. The latest Versions with their submission status. Running Tasks and Researchers. Capabilities, each working or broken, with its maintenance Task.
  • Conversation part: the mode. What the client sent with the last message (view, selection, references, attachments). What is absent.
  • The backend computes both parts from records, session context and tool checks, and updates them on events with no model turn.
  • Needs section ("I need from you"): the only part the agent writes, with ui.panel_set. It holds items that only the user can supply, and an item clears when the user provides it. The contract makes this section the one fixed place where clients read these items. Whether and how to notify the user is the client's decision.
  • Presentation: on demand, as an advanced feature that new or casual users do not see by default. Presentation is the client's decision.

B.2 Common rules

  • Prose fields (descriptions, claim bodies, where_it_stands) are Markdown in TEXT columns with an FTS5 index.
  • Ids: integer per table, shown as G-3, T-42, V-7, C-120, X-5, D-2. An optional fragment names part of a record (X-5#methods). Tools, context, evidence and UI all use this form, and one reference parser (C.4) reads it.
  • Each write: validate the whole change (JSON Schema for structured columns, rule checks for transitions), apply, append an events row. On refusal, report all problems at once. Constraints (CHECK, foreign keys, NOT NULL) and triggers hold even around the tools.
  • Actor: session:<hermes id> from HERMES_SESSION_ID117. user:<id>. harness. A platform write also records the identity it used (player or user).
  • Holds are leases (held_by, lease_renewed). The watcher clears stale leases.
  • Migrations: plain sqlite3, numbered SQL files, PRAGMA user_version.
  • Stored vs computed: the store keeps fields an agent or person decides (summary, see_also, tags, stance). Tools compute everything derivable from other records. (This completes the draft's unfinished "derived values" sentence.)
  • Each record tool returns the updated record, so agents never read a record back after a write.
  • Durability: daily encrypted host-disk snapshot at 06:00 UTC, seven kept140. Confirm while building that the workspace volume is on that disk.
  • Lost against files in git: line diffs and editor edits. events and store export cover most of it.

B.12 Completion, review and merge

  1. The Researcher calls task.complete. The tool checks that the type's linked deliverables exist (a commit on the Task branch, built Version, recorded claims, Experiment) and refuses, naming each absent one.
  2. A review wake (model, short Orchestrator Session) judges substance and requirements code cannot verify: it reads the Task, its Experiment results, new claims, and the Researcher's merge and submission_candidate answers. It accepts the work or reopens the Task with a reason, so the same Researcher Session resumes with that feedback. It decides merge: yes | no (reason) and carries any submission proposal forward.
  3. The watcher merges with no model when the review says yes: main clean, worktree clean at branch tip, --no-ff, re-run the mixin's build and check, then move main. Reuses today's integrate step, which refuses protected and generated paths, holds a host-wide lock and compares base with result28.
  4. A conflict or failed check leaves main unchanged and goes to a management wake, which resolves it in its own worktree, opens a maintenance Task, or asks the user. playerADE stops at a conflict and never forces it186. Here an agent still resolves it.

Orchestrator changes in its own worktree use workspace.change_complete and follow steps 2–4. Branches are kept whether or not they merge. Pause stops steps 2–4 for the agents' own work.

B.13 Dispatch, waits, recovery and messages

  • Runs API: POST /p/<profile>/v1/runs with session_id resumes a Session110. POST /v1/runs/{id}/steer injects guidance into a live run111. /stop stops it. GET /v1/runs/{id} reads its state.
  • Dispatch: start a run for an accepted (unclaimed) Task when dependencies are complete, a slot is free under max_researchers, and the workspace is not paused. high priority Tasks first. Idempotency key from the event. The run's first call, task.claim, takes the lease and makes the worktree. One researcher profile may hold several Sessions (spike S1 decides).
  • Kanban fallback if S1 fails: Kanban is the Task table, its triage status acts as proposed, extra fields go in a side table, and each run is a fresh attempt continued from handoff notes.
  • What the watcher follows: only what something waits on (waiting_on kinds) plus champion changes. Recent matches, rank and opponents are read live by the briefing, the tools and the away summary. The watcher does not watch every platform event.
  • Waits resolved without a model: xp (request reaches a terminal state), credits (balance covers the request, coworld credits --json), permit (user answered the platform ask), submission (a submission in progress reaches a platform state), platform (the failed route answers again), process (background process stopped), question (Orchestrator answered), user (setting or approval given), dependency (prerequisite complete, including a repair Task). Today's gate already polls XP, credits and permits29. The permit read path is fixed on the current profiles198.
  • Event ownership: the watcher's map from event kind to handler is data, and a test fails when any kind has two handlers. Today a chat turn and the cron job both act on one event199, and background results go to whichever session last called a tool200.
  • Recovery: resume a dead run with the same session_id. After recovery.max_attempts failures attach a fresh Session with a summary of the old transcript, the Task, its Experiment and branch commits. Then a management wake. Stuck Tasks (B.4) take the same path. playerADE never restarts workers automatically187.
  • Messages: task.ask records the question, sets waiting_on: question and wakes the Orchestrator. task.message/task.answer are delivered by steer if the run is live, otherwise on resume.
  • Uploads and XP are not tied to Task lifecycle: upload takes a Version id. XP tools record request ids on the Experiment at once30.

B.15 Tool checks and repair

  • Capabilities: each mixin command (build, check, upload, evaluate and game tools), the platform logins and CLIs, GitHub access and the build routes.
  • When: in the setup wake, at each release, daily, and at session start (the capability check, which writes facts into the briefing and replaces hard-coded "you have no X" rules in instructions).
  • How: real runs of each mixin command in the workspace environment. A dry-run or real upload for the upload route.
  • On failure, or on any tool error in normal work: mark the capability unavailable in capabilities. Create one high priority maintenance Task for it (repeats join the same Task). Tasks that need the capability get a dependency on it and are told when it completes. The repair Task takes the next free Researcher slot ahead of other work. After two failed repair attempts the user gets a ui.notify notice. Tool errors always show full output, exit code and context.
  • Profile machinery (store library, watcher, record and platform tool code) is fixed and read-only. Everything else that the agents work with is writable and fixable by the agents: game code, mixins, optimizer code (the per-Coworld policy-improvement code and tools), game tools, caches and skills. If the machinery breaks, dependent Tasks wait, the user is told, and the error is recorded for an upstream fix.
  • Environments: uv manages exactly two, on one pinned Python version: Hermes's interpreter (plugin only, fixed by the image) and the workspace environment (all tools and game scripts). A mixin declares other needs (another Python, Nim and similar toolchains) in its metadata, and setup installs them into the workspace tools/ folder.
  • Teaching: both profiles learn to diagnose, triage and fix whatever goes wrong (Python mismatches, API errors, absent or broken tools) and to keep working around a block.

C.4 Platform client, errors, references and the advisory hook

  • Platform client: the official Python client used by the coworld and softmax CLIs, kept current by the daily lock refresh (Appendix H), not a hand-written HTTP client such as today's credits workaround39.
  • Live resolution: league and game are always resolved live from the platform by id. A mismatch means resolve again, never refuse.
  • Errors: platform errors are temporary. Retry with backoff. If the error persists, the Task waits on platform with route, status and request id. The agent tries an alternative route if one exists. Recurring errors go to metta as bugs.
  • Nightly check: a read-only run against the real platform on a test Player calls every route the tools use. A failure blocks release and is reported to metta.
  • softmax_api: an escape hatch for routes with no tool, with auth handled (Player or User identity) and a route-list skill (softmax-api-routes). Calls are logged, and frequent routes become proper tools.

  • Tool-call format tests against the models in use. New capability ships through skills or softmax_api where possible, so it needs no restart.
  • Approvals: Hermes approvals.mode: off in both profiles (not smart). Hermes's hardline patterns for catastrophic commands still block, before any approval check, and are not configurable114. The current profiles already run with approvals off205.
  • No deny list. Agents may run any shell command, including ones that bypass the tools, and learn to do so only when the tools are insufficient or broken.
  • Advisory hook: recognises shell commands that bypass a profile tool (raw coworld submit or upload-policy, softmax login, force-push to the shared branch, file or sqlite3 access to .state/). It never blocks: the command runs, and a note in its result names the tool to use and points to the maintenance Task if that tool is broken.

Pause behaviour

no Researcher starts, background wakes, merges, recovery or autonomous submissions. Events queue and are processed in order on resume. User turns are still answered, and work the user explicitly asks for in a turn runs.

Watcher tick order

(1) check pause. (2) detect store writes without the library token. (3) read the champion (every 10 minutes). (4) resolve waits. (5) check runs, recover dead Sessions and stuck Tasks. (6) deliver pending messages by steer or resume. (7) do approved merges. (8) compute Goal conditions (ideation event for a Goal with no open Task, park event at the round limit). (9) run due tool checks. (10) start Researchers for free slots, repair Tasks first. (11) dispatch pending wakes. (12) write the heartbeat, the "has work" signal and the agent-context panel's computed parts. Events are events rows. Dispatch is idempotent on the event id (today's inbox uses sha256(session + prompt)58). An event is acknowledged only after its wake's run ends successfully. The bridge reads the heartbeat. When it is old, clients show "background work stopped since …". playerADE lost 1.5 hours when its tick was never installed189.

Sleep and drain

"has work" = a running Researcher run, a Task waiting on XP, credits, a submission or a background process, an open autonomous-submission window, or a queued wake. research workspace drain stops running Researcher runs via /v1/runs/{id}/stop, stops agent-started background processes, records both as "resume after wake", and returns when quiet. After the wake the watcher resumes those Sessions first with the same session id. If the drain fails, the pause behaves as today. A platform wake on events is a possible later optimisation.

Without the "has work" signal, autosleep ignores a Task that waits on XP, credits or a submission with no active run, and the workspace sleeps with the result outstanding. The watcher cannot wake a sleeping workspace. Its own reads do not delay sleep, because autosleep's idle clock moves only when a run or chat completion finishes105.

Wake: Hermes fires an overdue recurring cron job once when the gateway restarts106, so the first tick runs within about a minute of the wake. That tick is a full pass: it reads the champion, resolves every wait (including XP requests that finished during sleep), checks runs, resumes the drained Sessions before it starts new work, and dispatches queued wakes. cron.catch_up_missed must stay on, and prepare.py sets it. Tool checks rerun only when due, and the capability check runs when a Session starts.
