Implementation plan · November 4, 2026 · Proposed

Logging all agent operations to Datadog

As of ide 6ae5522, metta e6e4949.

Executive Summary

The goal is that everything about an agent's operation reaches Datadog. This covers requests and refusals for a Session (one agent conversation), internal Sessions, messages, every source of context, model requests and responses, reasoning and tool calls. It also covers the coordinator (the loops inside research serve that start and track work) and its logs. Records carry author, frontend, Session, run and turn where they apply. The detail goes down to the source of each token in each model call. Datadog replaces the workspace volume as the place to debug. Today Datadog has metadata only, plus partial historical content from October 27 to November 2. The code that produced that content was deleted on November 3.

In the plan, a plugin in each workspace captures records through the supported middleware and hooks of Hermes (the agent runtime). The plugin hands them to a background thread, which writes them to a local SQLite outbox (a table of records that wait to be sent). An exporter then sends them through the platform's existing authenticated route and storage to a new Datadog Logs consumer. An LLM Observability span (Datadog's record of one model call) is the reading view. No Datadog key enters a workspace. The first step sets Datadog access. All of engineering can read content, through a separate role and a separate scope on the token broker (the service that gives credentials to agents), so access can narrow later with no code change. This step is small and does not hold up later work. Every user's agent work is captured, and the settings page states this. With content kept for up to 6 months, Datadog Logs cost about $10.34 a month at measured peak traffic and list price, so cost is not a constraint at measured traffic. That figure counts inputs only, from traffic before recent changes, and it needs measuring again. A builder should read Appendix L first.

2 · How records get to Datadog
  • Workspace plugin → background writer → SQLite outbox → exporter → platform route → R2 (Cloudflare object storage) and queue → Datadog Logs and LLM Observability.
  • No workspace holds a Datadog key.
  • In long-running processes, the agent takes a quick copy of each record and does not wait for disk or network, and capture errors stay isolated from the turn.
  • Short-lived processes write directly, so a stalled disk can delay them and can make a calling tool time out.
  • A crash can lose records still in memory, and the plan reports that interval as unknown coverage.
  • Datadog Logs holds the exact copy. The LLM span is the reading view.

The plugin must stay stdlib-only and register quickly1, so it opens nothing at registration. Capture takes a stable copy of each record and hands it to one background writer thread in the same process. In the gateway, that thread strips secrets, hashes content and writes to SQLite, and the agent does not wait for those steps. Other processes put structured fields, hashes and sizes in their records, and no free text, so the gateway holds the only scanner in a workspace. Each workspace volume has one SQLite outbox, and one exporter process per workspace runs under its own restart supervisor. If the exporter dies, an alert fires and agent work continues.

A short-lived process, such as an ordinary research command, writes directly before it exits. When the memory queue is full, new records are dropped without waiting and are counted. A crash loses what is still in memory, and the plan reports that interval as unknown coverage.

One setting, IDE_TELEMETRY_DETAILED_CAPTURE, controls the detailed capture that makes the agent wait. On means capture runs. The image default is off until step 8 changes it, so a release cannot reach every workspace early, and the host turns it on for the test workspace. Step 3 builds that host setting. The code stays in place, so turning it back on needs no rebuild. The host sets it per workspace in the environment, and it applies at the next process start. See Appendix E.

The exporter sends to a submit-only route on the existing authenticated receiver, which derives workspace, owner and player from the credential2. event-ingest (the Cloudflare Worker that receives telemetry) stores to R2 and queues3, and a new queue consumer posts to Datadog Logs. The Worker, not the pod, splits content into log records of at most 24,000 serialized bytes. Before sleep, research workspace sleep asks each process that holds a queue to write it out, and then the exporter does a bounded drain. A runtime recycle, which recovers from uncertain execution, skips sleep, so each process also flushes when it is told to stop.

Platform API refusals go through structured stdout and the existing collector, so a pod that dies before collection loses the line. Browser observations use the logger of the product host, so an offline close loses records. Neither path sends body text. Local logs use a JSON log handler, and queue overflow counts as a gap.

The Logs timestamp is the delivery time, because Datadog accepts timestamps only up to 18 hours old. occurred_at holds the real time. Thus, a Session search covers the whole retained window, and the plan ships a tested saved query. See Appendix E.

3 · What each record holds and how records connect
  • There are four types of log record, called families. Each answers a different question.
  • All records use the same ID names and meanings, so one search by Session finds a Session's records. Shared content is reached through their manifests.
  • Text is stored once and referenced after that, so repeated history is not stored again.
  • These records help you work out what happened. They do not prove it in a dispute.

The four families

Take one model call in which the agent reads a file. Each family records a different side of it:

FamilyQuestion it answersExample
operationWhat happened?"read_file started", then "read_file finished, succeeded, took 12 ms"
contextWhat was added to a request, and by whom?"Our plugin added notice N-16 to this user message, at this position"
contentWhat was the actual text?The file text or a message, stored once. Also the manifest, which lists the pieces that made up a request
healthCan I trust that the logs are complete?"3 records dropped at 2:14", or "detailed capture was off during this period"

The families are separate because they behave differently. operation records are small and easy to search. content records can be large and are reused across calls, so other records point to them and do not repeat the text.

Shared IDs

IDs are labels such as workspace, Session, run, turn and tool call. Today, different parts of the system log different labels or none, so one search cannot find everything about a Session. In this plan, every record uses the same ID names and meanings and fills in the ones that apply. A health record may have no tool call, for example. A content record can be reused across calls and Sessions in a workspace, so it does not belong to one call. You reach it through a manifest.

Where each label comes from

Each label comes from the most trustworthy source available, not from what the sender claims.

  • Workspace, owner and player. The receiver is the platform service that accepts logs. Each workspace sends a secret key with its logs, called its credential. The receiver uses that key and the workspace being acted on to look up these labels. If the workspace's pod (the container it runs in) or a browser claims otherwise, the receiver ignores the claim.
  • Actor, meaning who did something. This has two separate fields. platform_actor is what the platform itself saw, such as who sent a request, and the receiver stands behind it. reported_actor is what a pod says about something inside the workspace, and it is only the pod's word.
  • Session. When a Session starts, a row goes into the workspace's own database. Later registrations can update that row144, so each record stores the values that applied when it was captured. A registered Session has a fixed Coworld and league194: records take session_scope, coworld_id and league_id from its stored binding, never from a workspace-wide current game. A conflicting open, message or transcript selection returns scope_mismatch195, and the refusal record holds both the requested selection and the stored binding. Hermes changes its live Session ID during compaction, so records keep the registered Session, the live Hermes Session and the Hermes task_id as separate fields145. That task_id is not the research Task.
  • Kind, meaning chat, wake or task. Records keep the database's label unchanged. Kind comes from the registration when one exists. The Orchestrator's hook registers an otherwise unregistered helper agent as chat, and the Researcher's hook does not register it196, so its kind is then unknown. Separate delegated and parent Session fields come from Hermes, and capture never invents a registration.
  • Order. Each process numbers its own records in sequence, and a record can name the record that caused it. The plan never assumes two records are related because their times are close, because clocks differ and many things run at once.

Stored once

A message or other piece of content is written once and identified by its hash (a fingerprint of the text). Hashes are shared within one workspace and capture policy, never across users. A manifest lists the pieces of a request by hash, and it is incremental: it names the previous manifest and lists only what was added. The tool list and the prompt sections each count as one reference. A Session's first manifest is full. So is the first one after compaction, proactive pruning (Hermes replacing old large tool results), another history rewrite or a capture gap, and one every 25 calls. This limits capture time and outbox size, because requests grow with Session length. With 6-month storage, a retained call stays rebuildable for at least 90 days from capture, less any delivery delay. See Appendix F.

Debugging records, not audit records

An audit record is evidence you can trust even if someone had a reason to lie. A debugging record is good for working out what happened, assuming nobody tampered with it. These are debugging records, because an agent has a terminal on the same disk as its outbox and could edit records before they are sent. The receiver can vouch for which workspace reported, and for what the platform saw itself. It cannot vouch for the text, times or actors that a pod reports. So do not use these records alone to prove who did something in a security or billing dispute.

4 · Capturing content
  • Our plugin can attach to Hermes's existing middleware points, which see main requests, tool schemas and responses with no size limit. This needs no Hermes change.
  • Generic hook payloads have size limits, so hooks supply lifecycle events and the few raw fields they pass, not full bodies.
  • Each context source is its own record, with its content, what added it, and when.
  • Five Hermes changes cover what middleware and hooks cannot see.
  • Each part of a request has its own source, so the logs can show token count by source at each model call.

The llm_request middleware point sees the full assembled api_kwargs, including tools4. A capture rig (a test setup) compares middleware output with what a provider receives. Until it passes, records are labeled assembled application requests.

Tool schemas and API instructions come from the full middleware request. Our plugin sections, notices and reactions come from our own code, one record each. The coordinator records the label, hash and size of each part of what it builds: Task, assignment, planning, wake, successor and resumed-chat prompts. The text comes from the model request, and hashes tie each part to it. A part that had a secret removed has a different hash, so it shows as unattributed. SOUL, project rules, memory and skills are captured at prompt assembly, and this needs a Hermes change.

The five Hermes changes:

  1. Prompt sources. Hermes records each section of the system prompt as it builds it, including at rebuilds and compaction. Token counts can then name SOUL, project rules, memory and skills.
  2. Every model attempt. Hermes records retries inside a stream, side calls to a model outside the main loop, and the partial text of a failed stream.
  3. Final tool result and persistence. Hermes records a tool result in the form it enters the conversation, including when a large result moves to a file. It also records native message IDs, persistence times and title updates, which no hook exposes.
  4. Run binding. Each record names its run, because hooks pass no explicit run.
  5. Flush before exit. The background writer gets a short, limited time to save records before the gateway exits.

Token count by source

The message explorer101 sets the level of detail. This dashboard steps through the model calls of a Session. At each call it shows input tokens by source, the request in wire order, the exact text of each row, the owner of the row and when the row is built. It is one use of these logs among others. Today it needs a copy of state.db, taken with kubectl exec under an elevated role, and calls in the middle of a Session are estimates102. Four things let the logs supply this data instead.

  • Separate parts. Through its manifest, each request names each tool schema with its owner111, each system-prompt section, and the visible text, reasoning and tool-call arguments of each message as separate objects. Each contribution to a user message has a UTF-8 byte offset and length, because Hermes joins typed text to an injection of memory and plugin text103. Wake instructions join the system message at request time104. Unattributed bytes are an explicit amount, so the parts add up to the captured request after the secret policy. This does not cover provider framing.
  • Usage for each attempt. Each attempt records prompt, input, output, cache-read, cache-write and reasoning tokens, requested and responded model, routed provider, finish reason, duration and first-chunk time113106. Returned cost needs its own capture, because the hook summary removes raw usage105. Missing usage stays unknown.
  • Token counts. The plugin records only characters and bytes, because it must stay stdlib-only. The writer stores a summary with characters and part hashes, and the exporter fills in tokens from outbox text. The exporter counts tokens once for each pair of content hash and tokenizer, caches the result, and it records the tokenizer that it used. It uses Hugging Face tokenizers when a model's tokenizer file is public, and tiktoken with cl100k_base as a stand-in otherwise. Tokenizer files are bundled in the image, and the model map lives in core/src/research_core/telemetry/tokenizers.py. The exporter runs in the workspace environment, so it can hold these dependencies, and the plugin cannot. A tokenizer failure leaves characters only and never delays delivery. Counts of separate parts do not always add up to the count of the whole, so each attempt keeps a signed difference from its billed size. That difference is not labeled as provider framing.
  • One summary for each attempt. A small record holds tokens and characters for 14 categories that do not overlap (SOUL, project rules, memory, skills, other system text, our plugin sections, tool schemas, typed user text, context added to user messages, assistant text, reasoning, tool-call arguments, tool results and unattributed), with tokenizer and category versions and prompt_hash. Datadog log analytics can then chart token share by source across Sessions. Row detail stays in the manifest, because one record for each row of each attempt grows with the square of Session length.

Milestone 1 separates typed text, hook text, usage, tool schemas, our plugin frames109 and matched SOUL text. The rest of the system prompt stays unattributed until Hermes change 1, because it can hold project files, caller text, memory and skills as well as Hermes text110. Internal stream retries and non-streaming probes run below the middleware107, so Hermes change 2 also records physical attempts. Until then, an attempt in the logs is one middleware call.

Exact means content after the secret policy. Reasoning that a provider never returned cannot be recovered, and truncation inside an external tool cannot be undone. The logs hold what the agent saw. A tool result is logged in the form the model received. When Hermes moves a large result to a file, the log holds the preview and path the model saw, plus the original size. If the agent later reads that file, the read is logged like any other tool call. An attachment is logged as the model received it. research serve prepares attachments before the run starts, in a separate Hermes interpreter that returns only a changed message182183. So that step must also return the original size, type, change made and transcription outcome, and research serve records them by admission ID. File names and text reach the logs only through the model request. Output that the agent never saw is not logged. Neither is text that never reaches a model, such as a refused request body or a message that fails before a run starts. Records never claim a "complete Session" when a known gap exists, and a Session can still have losses nobody detected. Token-by-token stream history is left out. See Appendix G.

5 · Access and privacy come first
  • Step 1 sets who can read existing prompts and new content. It is small and does not hold up later steps.
  • All of engineering can read content. Datadog Restricted Datasets apply this to both Logs and LLM Observability.
  • The auto-approved datadog.read broker scope loses access to new telemetry and to prompt spans, though not to existing diagnostic logs, which can hold request text. Agents ask for a separate scope by name, so access can narrow later with no code change.
  • Secrets are removed in the workspace before storage, then again at Datadog. No detector is perfect, so readers can see a secret that passes.

Existing spans hold prompts, and 92 of a 200-span sample carry sensitive_data tags (those tags do not show that the data was redacted). Restricted Datasets limit data by query to named Teams or Roles. Log restriction queries cover Logs only, and permissions add up across roles, so one broad role defeats them.

datadog.read is auto-tier5, and an application key has its owner's access. So the owner of the datadog.read key gets no dataset membership and no unrestricted access. A new auto-tier datadog.content.read scope has its own key, which is in the dataset. An agent gets content by asking for that scope, with no approval step, and the broker records who asked and why. If the dataset setup meets a real obstacle, content ships anyway and access is fixed afterward.

The gateway removes secrets before the hash and before the outbox write. The background writer does this, so unstripped text waits in process memory until then, and it never reaches disk or diagnostic output. Sensitive Data Scanner (Datadog's redaction product) is the second layer. It acts after data leaves the workspace, so it does not replace the first layer. The settings page must state the real scope, readers and retention of up to 6 months, and the 30-day R2 trace retention, before capture turns on for every workspace.

Secret removal has one scanner and one list. Our plugin adds the Softmax token formats to Hermes's existing secret patterns. Hermes then hides those tokens in terminal, file, code and MCP output, so the agent does not see them there. The gateway writer runs Hermes's redact_for_egress over everything it captures, including text Hermes does not scrub, such as tool arguments and user messages. No other process puts free text in a new record, so no other scanner is needed. Existing diagnostic logs are the exception: the seam's and coordinator's error logs and the browser's automatic error forwarding already reach Datadog, and they can hold text from a request. Only Datadog's scanner covers them. Datadog's scanner is a safety net configured with the same formats. No detector finds every secret: a password in ordinary prose or a secret inside an image can pass, so readers can see what passes. A test with planted fake secrets measures the misses before rollout. Capture covers every user, with no opt-in or opt-out. The detailed capture setting is per workspace and records carry their capture status, so opt-in can be added later with no redesign. No procedure exists to delete one person's stored content, so it stays until retention ends. See Appendix H.

6 · Volume, cost and limits
  • With content kept for up to 6 months, Datadog Logs cost about $10.34 a month at measured peak.
  • 14% of measured model requests exceed 1 million characters, so the reading view must handle large requests.
  • A per-workspace daily limit stops a looping agent from flooding Datadog.

The LLM span is the main reading view. The Logs consumer builds the projection by walking the manifest chain in R2, with content objects keyed by workspace and hash, and anything no longer in R2 appears as an omission with a Logs link. The projection sends everything when it fits, and otherwise a size-bounded selection with Logs links. Thus, a span is not always exact, but Logs is.

The receiver rejects new body uploads above 1 GiB per workspace per Pacific day. The exporter then records a gap and turns continue. This limit, the 256 MiB local pending limit, the memory queue limit and the index limit of 250,000 records a day each log and alert when reached, so it is quick to see that one needs raising. The stress row is demand before limits: about 450,000 records a day exceeds the 250,000 cap, so the real result would be a lost index and a smaller bill. See Appendix I.

8 · Proving it is complete
  • A reconstruction of a Session uses only Datadog APIs.
  • CI fails when an emitted event type or a prompt section has no declared capture outcome.
  • Monitors catch pipeline failures, not every lost record.
  • The message explorer's data must regenerate from Datadog alone.

A registry compared with itself proves nothing, so the plan compares an independently observed provider request and committed results with the reconstruction. One synthetic Session runs this on a schedule, and an alert fires if it stops.

A concrete test sits alongside the failure and completeness tests. It regenerates the data of the message explorer for a real Session using only Datadog APIs, then compares it with a state.db copy of that Session. An empty queue, an accepted upload or the absence of a gap marker does not prove completeness on its own. See Appendix J.

Appendix E · Delivery detail

The workspace path

The plugin runs in the Hermes interpreter. Capture is stdlib-only. The design reuses the responsibilities of the deleted tracer but not its code, because that code imports pydantic and httpx48.

The outbox uses WAL mode (write-ahead logging, which gives concurrent readers and one writer). Each row carries its profile (one configured agent, such as the Orchestrator) and Session, and each writer creates and owns its connection. The host runtime owns the exporter. The runtime exits the container when the gateway or seam exits49, so the exporter supervisor stays outside that fatal wait set.

The receiver is hermes/traces-style, and the new route is a sibling of it, at POST /v2/workspaces/{workspace_id}/telemetry/logs. workspace_id is the workspace's provisioning ID, which the image already uses for /v2/workspaces/{workspace_id}/connection. The route reuses the check that binds a workspace credential to its installation208186. It does not reuse ingestTraces, which rejects old events before storage184, because that would fail delayed delivery. The API route handles auth, the daily limit and resend_age_days. The Worker handles R2, the queue and chunking. The new admission accepts an old occurred_at, and the 24-hour rule applies only to the LLM span. A content hash is separate from a delivery identity: a retry reuses the identity, and a resend makes a new one. event-ingest has no Logs destination today, only ai-datadog.ts and posthog.ts. The new queue consumer posts to /api/v2/logs with its own retries.

Worker-side splitting gives one R2 object and digest per logical content. The 24,000-byte bound exists because Datadog recommends at most 25 KB per log36 and grouped views truncate larger fields.

The route acknowledges a record after R2 and queue admission. Retries use the same ID, so duplicate delivery is allowed. Conflicting hashes are errors. Invalid records go to a quarantine queue. Logs and LLM acceptance are tracked separately. After the flush below, the drain extends the existing sleep preparation50, with a bounded drain. If intake is down, rows stay and sleep proceeds, and the rows drain on wake.

Searching late records

A Session search covers the whole retained window and then sorts by occurred_at, which gives rough time order. True order comes from sequence numbers and causal links. A search of only the original day in the time picker misses late records. LLM intake rejects spans older than 24 hours51, so those get a health reason and only Logs has them.

The background writer

Who writes. The gateway and the seam are separate long-running processes123, so each has one writer, shared across its profiles. Store-only tools, delegated agents and cron jobs that run inside the gateway share its writer124 125 126. The coordinator loops run inside research serve137, so they share the seam's writer. Ordinary research commands, workspace-tool subprocesses and external cron workers write directly before they exit124. The name does not decide this, because research serve is a service. Only the gateway's writer handles free text. Capture binds profile, Hermes home, Session, run, attempt and capture policy before handoff. The writer never reads these from its own environment. Sequence numbering and queue publication are coordinated, so concurrent callbacks stay in order. Sequence numbers show capture order, and causal IDs show execution order.

Snapshots. The queue holds an owned, stable copy, never a reference to live history, responses or arguments. Immutable strings need no extra copy, and an existing isolated middleware copy can be reused. A shallow-copy fallback does not count as isolated. If a snapshot fails, the record says content is missing, and the writer does not read the live object later.

Wait limits. SQLite's busy timeout starts at about 250 ms, and transactions stay short. This limit covers waiting for another writer, not total disk time127. The writer keeps a record in its queue and retries with increasing delays, within the memory limit, and it does not retry malformed records. A short-lived process has one total budget across its records, not one limit per record. A stalled disk can still hold up a short-lived process, because no limit inside that process can interrupt the write, and that delay can make a calling tool time out.

Emptying the queue before a stop. research workspace sleep runs in a different process from the gateway50, and its exit code 0 promises that nothing is held in memory115 116. So each writer registers when it starts. The sleep command waits until its existing drain has finished and the store connections are closed. Before it flushes the databases and before the exporter drain, it writes a flush request to a local file, and each live writer commits everything captured up to that point, including the item in progress, and replies. An empty queue alone is not proof. research serve keeps applying transitions while paused138, so a pause does not stop new records. So sleep has two separate confirmations. First, the command tells research serve to stop its coordinator loops, and research serve confirms this without waiting for any telemetry writer. An unconfirmed stop is an application failure: it goes in volatile, the command exits 1, and any loops this attempt stopped restart. Second, one 10-second deadline covers writer replies, the exporter drain and the final outbox checkpoint and fsync. That work runs outside the sleep command's process, so it cannot hold the command past the deadline. A timeout, a locked outbox or a failed checkpoint goes only in a telemetry_gaps field and does not prevent exit 0 (D40). The records it covers are unknown coverage, not a known lost count, and the writer's next start sends a gap record. If intake is down, committed rows wait for wake. The loops stay stopped until wake. Step 4 updates the sleep contract documentation with this telemetry exception.

Other stops. Sleep is one of four ways a runtime stops:

  • Sleep uses the flush above.
  • Recovery recycle. The runtime exits on purpose to settle uncertain execution, and it skips sleep139 140. It emits workspace_runtime_recovery, which the plan captures with the boot identity. Children get SIGTERM, then a kill after 10 seconds117.
  • Ordinary termination follows the same signal path. research serve flushes on SIGTERM, in step 4. The gateway cannot, until Hermes change 5, because Hermes ends with os._exit, which skips atexit114. Change 5 adds a bounded flush before that exit, within the 10 seconds. A plugin writer thread cannot do this alone.
  • A forced kill or crash loses what is in memory.

A writer that does not confirm reports unknown coverage for that process. A flush must never hold up recovery beyond these limits.

Loss accounting. The queue limit covers queued, in-progress and retried records, in bytes and in count. The starting limit is in Appendix I. A drop adds to a bounded counter outside the queue, and a gap record follows when possible. Records distinguish queued, committed locally and admitted centrally. A restart can identify a process that did not close cleanly or events that other records show are missing. It cannot recover or count the rest, so the plan reports unknown coverage. The plan makes no claim about how many records a crash loses until this is measured.

The detailed capture setting. IDE_TELEMETRY_DETAILED_CAPTURE on means detailed capture runs. The image default is off until step 8, and on after that. Off stops detailed capture of requests, responses, tools, context, attachments and store and admission content, along with its work on the agent's thread. Short-lived processes skip their detailed writes too. With it off, the plugin does not register its full-request listener119. Other listeners can still cause the copies, and Hermes always copies tool arguments119. Token usage, timings and health stay on through post_api_request17, at a small measured cost that is not zero. Records carry the setting's value and configuration version, and health records mark known off intervals, because a missing record alone does not prove logging was off. Turning it back on starts a full manifest and does not backfill. Tests cover both values, so both paths keep working. The host sets it per workspace, and it applies at the next process start. No such setting exists today: the pod builder passes only BUILDKIT_HOST199 and the installer rebuilds that template200. So step 3 adds an optional per-workspace override in metta, stored on the workspace record so that it survives restart and image adoption, and set only through an elevated team-member route, because an owner-writable setting would be the opt-out that D35 rejects. Step 3 adds the stored value to pod_spec in workspace_pod.py. Automatic wake and explicit Resume today change annotations only, and the reconciler then raises replicas from zero. So step 3 applies the value at the shared stopped-to-running step, before replicas rise: wait until the earlier pods are gone, rebuild the template from the selected runtime and current value, and keep the existing resource-version checks. This covers automatic wake, explicit Resume and maintenance release. The setting route only stores the value and never rewrites a running workspace's template, because a changed template would restart its pod. The value takes effect when the next pod is created, not when a container restarts inside a pod. Step 4 reads it before capture starts and adds it to the environment lists that image/runtime.py builds201, and to the keys prepare.py keeps, so short-lived processes see it. With no override, the image default applies.

Upload limits and the edge paths

Upload limits. Pods upload whole content objects within the existing limits of 4 MiB per event, 5 MiB per batch and 50 events52. Larger content splits at the pod into ordered segments with a root digest. A log record normally holds about 16,000 bytes of text in message.

API refusals. Refusals use structured stdout through the existing collector53. A refusal has stage, reason and size, with no body text. The validated operation-argument bound is 256 KiB54. Malformed input before validation has no such bound, so size is recorded as far as it was read. A durable platform table was judged not worth a new subsystem.

Browser. The product host already initializes datadogLogs with error forwarding, 100% session sampling and URL cleanup55, and /ide-next belongs to that app56. A small connectOperationLogger(callback) export, in the pattern of the existing analytics seam57, gives the IDE package that logger with no new dependency or token. The gateway captures submitted text once it reaches a model request. The browser sends IDs, outcome and length for local refusals, abandonment and delivery, with no text. Browser identities are claims, joined to server records by operation ID. Standalone /ide-final sends nothing to Datadog. Ad blockers also lose records.

Local logs. The handler is a JSON logging.Handler that the plugin installs, once per gateway process. Bare -v is rejected because its formatter has no profile or Session58 and a gateway serves several profiles. Hermes stamps hermes_home and session_tag on each record59. The handler redacts with the same function, puts the line on a bounded queue, and a listener writes stderr. It never writes SQLite on the gateway's event loop. File tailing is not used. This queue is separate from the background writer, so it needs its own bounded drain at shutdown, and its redaction counts as work the agent waits for.

A request manifest lists ordered roles, content parts, tools and options with references. Content by hash does not exist to save Datadog money. The LLM span shows one attempt directly (see Section 6). For the exact copy, the Logs link opens the manifest and a reconstruction command, which assembles the request from Datadog alone.

Incremental manifests. The writer builds each manifest from the snapshot of that attempt, after it strips secrets. It compares the complete ordered history with the previous committed manifest, and it writes an append only when the previous history is an exact prefix. Length, object identity and a compaction hook are not enough, because fallback, compaction and proactive pruning can change existing messages146121 122. Otherwise it writes a full manifest. Each manifest records the current tool-list and prompt-section hashes, model, provider and options. Each of those two hashes points to an object that lists the individual schemas or sections with their owners. Retries with the same history stay distinct attempts, and internal stream retries still need Hermes change 2.

Baselines belong to one Session and history line, never across profiles, auxiliary calls or delegated Sessions. A full manifest starts a Session and follows compaction, a rewrite, a restart without a verified baseline, capture being turned back on, a capture-policy change and a capture gap. One is also written every 25 calls, and that is an extra trigger, not the usual interval: pruning can force a full manifest on several calls in a row. A full manifest does not send bodies again if they are still held. When pruning replaces a result, records keep the original and replacement references, the message affected and the policy. A baseline advances only after its manifest and new content commit, so a failed or dropped capture cannot become the hidden parent of a later manifest.

Resend age. The outbox database keeps one small row for each object: its hash, status and last accepted time, with no text. The exporter updates the row from each reply, and the writer reads it at each capture. When a new call depends on something that was rejected or last accepted longer ago than the resend age, the writer sends it again from the request it holds, or writes a new full manifest. This covers every dependency, including earlier manifests. Content is found by hash, so a later copy also repairs earlier manifests. If no later call uses a rejected object, the earlier calls stay incomplete and a health record says so.

The workspace does not know the retention period. The receipt gains a resend_age_days field185, and the outbox keeps the latest value. Nothing is old before the first reply, so no default is needed. Retention and resend age sit together in one metta setting, so a retention change needs no image or profile release, and it applies to new captures. A metta test fails if the resend age is more than half the retention, so a capture-time check leaves each accepted dependency at least half the retention, from capture, while retention does not change. Delayed delivery uses up that time: a call can arrive incomplete even when every record was accepted. Reconstruction reports the missing dependency, and later reuse can repair it.

What accepted means. Accepted means durable admission to R2 and the queue, not storage in the Logs index. Records past the index quota are not indexed, so they are lost from Logs, and a health record reports this. They are not sent again until the resend age passes. An outbox row's text is deleted once the row is accepted, or after permanent rejection.

What a retained call depends on. A retained call needs its base manifest, the manifests between, the tool and prompt objects and all referenced content. With 6-month storage and a resend age of 90 days, every call stays rebuildable for at least 90 days from capture and content can stay up to 180 days, provided Logs accepts every dependency. A later full manifest makes later calls independent, but it does not repair earlier ones. Rebuilding one call walks back to the last full manifest. A missing link blocks that call and the later ones until the next full manifest. Each manifest names the previous one, so the gap is visible.

Durable commands and held chats

A tool returning no longer means its change happened. A tool can save a command, wait 15 seconds and return transition_pending, and the coordinator applies or refuses it later141. So records separate tool response, command acceptance, application or refusal, native admission and native completion. They capture accepted work even after the originating tool or worker has ended.

A failed chat can wait and later resume under the same admission and Session, with a new run152. Resuming sends a generated continuation prompt, not the original message, and the native-message hook skips it153. So each failed run is captured before its receipt is cleared, with its classification, hold deadline, resume count, and old and new run. The continuation text comes from the model request that carries it. The continuation's author is the coordinator, even though it reaches the model in the user role. Records distinguish transport replay, a resumed chat and a worker successor.

Debugging, not audit

A reader can rely on platform_actor, receipt time and the identity derived from the credential. Everything else on a pod-reported record is the pod's word. It is possible that an agent can read the workspace credential. Server observations stay separate. The route is submit-only64, and tests prove that the pod credential cannot read Datadog, R2 or another workspace.

First layer. There is one scanner, in the gateway writer, working on whole content before hashing.

  • Softmax formats. The plugin calls ctx.register_redaction_patterns166 once for each of usr_, ply_, cga_, mch_, cmr_, rrt_ and xpw_168. It covers these formats, known vendor prefixes, secret-named assignments, JSON fields and bearer tokens. It fails closed, so an error never returns raw text128. The plan accepts this for prefixed tokens, because about 38 of the 44 body characters stay hidden. Records state how many values were removed, with no hash of the raw secret. The coordinator's prompt-part hashes are the one hash taken before secret removal, because the coordinator has no scanner. Each covers a whole part, so it does not expose a secret unless someone can guess the whole part.
  • Effect on the agent. The patterns join Hermes's global list, so terminal and file output170 171 show the masked form. Our own plugin tools, including softmax_api, are not scrubbed before the model, so a token they return still reaches the agent, and the scan keeps it out of the logs. A real-Hermes test confirms that no workflow needs a token's value.

Limits. Patterns miss secrets with no recognizable format, such as a password in prose, and they cannot read images. Random keys with no prefix, such as service_key, match no pattern. If the test shows these appear, Hermes's exact-value list167 can hide them with one call, within its limit per profile. That call runs per routed profile, and the lookup uses the Hermes home of the current context187. Appendix L · Orientation for a builder

The goal. James Boggs asked for everything about agent operations in Datadog, so that debugging no longer needs a copy of the workspace volume. "The owner" in this plan means James. "Workspace owner" means the user who owns a workspace.

Repositories. ide: is softmax-universe/ide-distributions: the Hermes profiles, the plugin and the image. metta: is softmax-universe/softmax, still called metta here: the platform. The platform API is under workspaces/observatory/platform, the receiver is the Cloudflare Worker in packages/event-ingest, the IDE is packages/softmax-ide (/ide-next is its route, and /ide-final is a standalone build) and the product host is workspaces/web/web-client. Spacelift applies devops/tf/ after a merge. hermes-canary is the Kubernetes namespace of the canary workspaces. hermes: is the public nousresearch/hermes-agent image, installed at /opt/hermes.

Processes in one workspace pod. image/runtime.py supervises all of them192.

  • Gateway: python -m gateway.run, in Hermes's Python environment. It runs the agents and loads our plugin, which can use only the standard library.
  • Seam: research serve, in the workspace environment. It takes messages and actions from the platform and holds the coordinator loops. image/application.py is the interface the platform uses to reach it.
  • Exporter: new in this plan, in the workspace environment.

Release. A push to main under image/, core/, orchestrator/, researcher/ or the root lock dispatches metta's image release191. That publishes a candidate. Qualification, promotion202 and workspace adoption are separate stages, and healthy running workspaces can keep an older image203. So deploy and verify the receiver before releasing what sends to it, and verify adoption before relying on a change. To adopt on the test workspace, wait for promotion, pause it through the lifecycle API and wait until its pods are gone. Keep it paused until adoption has selected the promoted runtime: check the stored runtime and the Deployment template image against the promoted runtime's image, and the Deployment's selected-runtime annotation against its release_digest, which is not a container digest. Then resume it and check that the running pod uses the promoted image. A wake before adoption can keep the old image. Keep existing application operations and the context contract compatible throughout. Telemetry records have their own schema version, so they do not change the context contract version. A public application-shape change needs regenerated artifacts and updated consumer pins206, and a breaking context change needs a coordinated cutover207.

Terms.

  • Session: one agent conversation. Turn: one prompt through to the final answer. Run: one execution that research serve starts for a chat, Task or wake. Model attempt: one observed model call. Before Hermes change 2 it is one middleware call, which can hide internal retries. Execution attempt: a durable research execution, identified by client_admissions.op_id and referenced by an assignment's current_attempt_id.
  • Profile: one configured agent, the Orchestrator or a Researcher. Goal and Task: research plans that the Orchestrator makes, and work that a Researcher does.
  • Wake: a prompt that the coordinator sends to start work without a user message. Successor: a new Session that continues a Task after an earlier Session stopped. Admission: the seam's durable acceptance of a Session-open or message operation, including internal execution messages.
  • Stores: the workspace SQLite database holds Sessions and admissions, and each Coworld has its own SQLite database for Tasks and Goals. Both hold events. Hermes messages are in each profile's state.db. Notices, reactions and away summaries: text our plugin adds to a user message. Batch Session: one wake that covers several events.
  • Owner instance: the coordinator applying a durable command. Lease epoch: the generation of a Task claim held by a Session, which a command keeps from its issuing actor. Boot identity: IDE_RUNTIME_ID, new at each image-runtime start, including a container restart in the same pod. volatile: application work or database-flush failures that prevent safe sleep. telemetry_gaps: unconfirmed telemetry that D40 leaves out of that decision. Drain: sending or writing everything queued before a stop.
  • Quarantine queue: where the receiver puts invalid records. Poison event: a record that always fails to process. Retired and waking refusals: requests refused because a workspace is retired or still waking.
  • Standard tier: Datadog's normal searchable log storage. Flex: its cheaper long-term tier. Data Access Control: the Datadog feature that holds Restricted Datasets. ml_app: the tag that names an application in LLM Observability. Codex paths: Hermes request paths for OpenAI Codex, which the shipped profiles do not use. prompt_hash: the hash of a whole system prompt.
  • Gap: a health record that states data is missing. Capture policy: the setting and disclosure version under which a record was captured.
  • Auto-tier: a broker scope that vends with no approval. Enrolled agent: a client registered with the broker.
