Research Report · November 2, 2026 · Triage briefing for James

Triage: the $10-in-27-minutes incident and its three Asana tasks

This briefing for James Boggs covers JAME-176 (runaway tool-call loop), JAME-175 (dispatcher error classes) and JAME-174 (budget-aware research serve). As of ide-distributions 2a224d2d, metta 5a41cd9aa2 and Hermes v0.21.6 source. All times are PST.

Executive Summary

The workspace's $10 key ran out in 27 minutes. The user's chat did not loop: it made 2 valid claim calls and cost about $1.00. About half the money, roughly $5.00, went to 14 Orchestrator wake Sessions, all created in the same second. The Orchestrator is the research-lead agent that the user chats with, and a wake Session is a background run that the watcher starts to handle one event. The watcher's first champion sync read every league on the platform, because the active Coworld (Generals) has no league1. It reported 14 champions from other Coworlds (other games on the platform) as changes and started one wake per league. Each wake tried to record a claim, the model kept dropping the claim's summary and tags, and the loop guard of Hermes (the agent runtime) only warned. One wake sent identical arguments 185 times. The setup wake, which is ordinary work, cost about $3.20, and the Researcher about $0.90. All 14 wake events are acknowledged, so unpausing workspace 58bda2da starts nothing again.

The single budgeted key did its job as a hard cap. What all three tasks miss is a record of why model work cannot run now. Each run start goes through one gate, inference.available()2, and that gate checks only the expiry of the key. We recommend this order. First, sync champions for the active Coworld only, merge champion wakes, and turn on the Hermes hard stop with a notice when it fires. Then add one shared record of why model work is blocked, written from Hermes's own error classes and read by the gate, the dispatcher and the IDE. Claims stay in the wake prompt. Making them reliable on mid-tier models is its own task, together with tool-call tests across several models. Section 6 tells how each ticket changes. Not examined: the Datadog logs, the transcript of the Researcher Session (its cost is estimated as a remainder), and the Hermes build inside the image.

1 · What actually happened
  • The chat Session did not loop. The chat Session api_1793654344_5866fc18 made 2 claim calls, both action=query, and cost about $1.00.
  • The trigger was the first champion sync of the watcher at 1:31:54 PM. It emitted 14 champion.changed events, one for each league, all for leagues in other Coworlds.
  • Each event started its own Orchestrator wake Session. 9 wakes started work at once, and 5 started about two minutes later. That agrees with the limit of 10 concurrent runs in the Hermes gateway.
  • The wakes made 357 claim calls, and 348 of them were writes. The tool refused 345 writes because summary, tags or both were missing. 3 writes succeeded.
  • One wake made 193 claim calls, and 185 of them had identical arguments. That wake alone cost about $3.00.
  • The money split roughly in thirds. The champion wakes cost about $5.00, the setup wake about $3.20, and chat and Researcher about $1.90 together (Appendix A).
  • The key ran out at 1:46 PM. The user's next three messages failed with "HTTP 403: Key limit exceeded".
Terms used in this report A Coworld is one game on the Softmax platform, and a league is a competition inside a Coworld. One Coworld can have several leagues. A Player is the user's platform identity. The champion of a league is the policy version that represents that Player in the league. The Orchestrator is the research-lead agent profile that the user chats with. A Researcher is a worker profile that does one Task in the background, and Flint is the free model that Researchers use by default. The watcher is the periodic job of the Orchestrator. It syncs platform state and starts wake Sessions. The lease is the time-limited OpenRouter key, with a dollar limit, that the platform gives to a workspace. The workspace records the expiry of the lease in a file named .inference-lease.

The task statements built their story from Datadog logs3. Those logs cut tool arguments short, and they do not name the Session. The ops route session.messages gives the stored Hermes messages with full arguments4. The workspace.snapshot route lists each Session with the event that triggered it, and run.get gives the status and token usage of each run. The OpenRouter activity report for the key gives the exact dollars for each model5. Together, they show three causes, one on top of the other.

Many runs from one event. leagues_of returns the leagues whose Coworld is the active one, "else every league the platform lists"1. The design rule that it implements, A4.9, says "every league of the active Coworld's game"6. The fallback goes further than the rule. The platform lists 501 leagues, and none of them belongs to Generals7. Thus the step pulled in all 14 leagues where the Player has a membership. champion.sync treats a league with no stored row as a change8 and emits champion.changed8, which starts a model wake9.

The watcher joins repeated events into one Session only when they share a kind and a subject10. The subject is the league id, and thus 14 leagues gave 14 Sessions. Only the gateway held them back. The Hermes setting gateway.api_server.max_concurrent_runs has a default of 1011.

Dropped arguments. The wake prompt tells the model to "record a claim about the new champion"12. The model sent body, evidence, see_also, stance, status and superseded_by, but not summary or tags. Several of those fields belong to other claim actions. The schema of the claim tool requires only action. "Required for write" is only in the description text, and no provider can enforce that. Replays from earlier the same day showed the pattern. On the default routing of OpenRouter, Kimi K3 dropped required arguments in 3 of 3 tries. On the endpoint of Moonshot (the maker of Kimi), it dropped them in 0 of 3. In this incident, every Kimi call went to third-party hosts (Wafer, Relace, Modal and others), never to Moonshot.

Nothing stopped it. Each refusal is JSON with an "error" key13. Thus the Hermes loop guard counted each one as a failure and attached a warning, and the model ignored the warnings. Hermes turns on its hard stop only for platforms that it treats as unattended. The IDE runs on the api_server platform, and that platform is on the attended list14. Each wake ended only when its model gave up.

The model settings at the time. The workspace used moonshotai/kimi-k3 with no host pin. PR #137 (clearer refusals, merged 3:05 PM) and PR #138 (Kimi K3.1 Pro as the default, and the two Kimi models pinned to the Moonshot endpoint15, merged 3:35 PM) both landed after the incident. PR #118 made the model a profile setting that the workspace setup code never changes16. As a result, existing workspaces keep kimi-k3, now pinned, until the user changes it. These changes reduce the trigger, but none of them caps a loop.

2 · Shared concerns across the three tasks
  • One budgeted key is the cap, by design, and it held. Chat, wake Sessions, Researchers and the fallback model all draw on one $10 OpenRouter key. Without that limit, this incident would have cost much more.
  • Nothing says why work stopped. When the key is spent, each consumer fails with a raw provider error. Nothing tells "budget spent until 4 PM" apart from an outage or a bad request.
  • Each run start already goes through one gate. HermesRuns.start refuses a run when inference.available() is false2. This is true for chat, wakes and Researchers. Thus a change to inference.available() covers all of them.
  • inference.available() knows one fact. It checks that the lease file exists and that its expiry is in the future17.
  • Hermes already classifies provider errors. Hermes puts each failed model call into a FailoverReason class, for example billing, rate_limit, overloaded or context_overflow18. A 403 "Key limit exceeded" goes into billing. Plugins receive the class through the api_request_error hook19.

Tasks 2 and 3 each propose a part of the same thing. Task 3 (JAME-174) proposes a marker next to .inference-lease. Task 2 (JAME-175) proposes an error class stored on each chat admission. An admission is the client_admissions row that the dispatcher keeps for each user message. Task 1 (JAME-176) proposes spend-rate alarms that pause the workspace. One small JSON file next to the lease file, .inference-state, serves all three better. The file says why model work is blocked and until when. It is a file, not a store table, because three separate processes use it: the Hermes plugin, the lease loop in the image, and research_core. From here on, this report calls it the inference state.

Who writes it.

  1. The profile plugin registers an api_request_error hook. The plugin already registers hooks20. On billing, the hook writes budget_exhausted. After repeated overloaded or server_error results, it writes provider_unavailable with a retry time a few minutes later. It also records the last class against the run of the Session, so that the dispatcher can read it.
  2. The lease loop in the image21 writes the next refill time next to the lease file. It also writes budget_exhausted itself when the platform refuses a lease because the budget is spent.

Who clears it. Only the lease loop clears budget_exhausted, when it installs a new key. A new key is the only thing that ends a budget block. Nobody clears provider_unavailable; it lapses at its retry time.

Who retries. Nothing calls the model to test whether it works again. Each consumer checks the gate before it starts work, and waits while the gate is closed. The dispatcher holds a chat message as waiting and resumes it when the gate opens (Section 4). The watcher leaves wake events unclaimed while the gate is closed, so no attempt counts against recovery.max_attempts10. Researcher dispatch skips its tick. The task statements miss the last two, because task 3 talks only about chat messages.

3 · JAME-176: find and stop the runaway tool-call loop
  • The cause is known. A champion sync that read every league started 14 runs, the model dropped required arguments, and the loop guard only gave warnings. The transcripts answer the four questions of the task (below).
  • Sync only the active Coworld. Remove the "every league" fallback in leagues_of. A Coworld with no league has nothing to sync. In this incident, that removes all 14 wakes, about $5.00.
  • Merge champion wakes by kind. Coworlds do have several leagues: Cogs vs Clips has 3, and Sugarscape, webDiplomacy and Crewrift have 2 each. Thus one sync can still raise several changes, and one wake should handle them together.
  • Warn, then stop. Hermes already warns after 2 identical failures or 3 failures of one tool. Turn on its hard stop, and post a notice when it fires. A halted run ends completed, so the watcher does not retry it.
  • Keep the claim in the wake prompt, and make claims reliable. The fix belongs in the tool schema and in tests against mid-tier models, not in avoiding claims.
  • Defer the spend-rate alarm and the limit on parallel calls. The wakes never made more than 2 tool calls in one model message. The many concurrent Sessions multiplied the cost, not parallel calls.

Answers to "What to find out"

  1. Arguments. The model omitted summary and tags completely. It did not nest or rename them. In their place, it sent fields of other claim actions (Appendix A).
  2. Which Sessions. The calls came from 14 Orchestrator wake Sessions for champion.changed, and 6 calls came from the setup wake. They did not come from the chat Session or from delegated subagents. The Researcher Session (1:35 to 1:43 PM) cost about $0.90. The ops route does not serve its transcript, so its calls are not counted.
  3. Model or schema. Both. The host dropped arguments, as the earlier replays show. The schema allows it. claim is one tool with six actions, its only required field is action, and the fields of write, search and retire sit next to each other. The description of tags even says first that it is a search filter ("Keep only claims carrying all of these tags"), and only after that "Required for write". PR #137 now refuses fields that belong to other actions and shows an example.
  4. League selection in Context v1. Context v1 is the context block that the IDE adds to each chat message. This report did not check the league selection. The platform.active_policies refusals came from the chat Session. That question is separate from the spend, and it needs its own small check.

What to change, in order of value per effort

  1. Champion sync reads the active Coworld only. leagues_of returns only the leagues whose game.coworld_id is the active Coworld22. When there are none, the sync step records that it has nothing to sync. The first sync of a workspace still emits champion.changed for each league of the active Coworld, because the user should hear who represents them there. The 14 rows already in the Generals store stay. They are a correct record of those leagues, and the sync does not read them.
  2. Hard stop, with a notice. Add tool_loop_guardrails: {hard_stop_enabled: true, hard_stop_after: {same_tool_failure: 5}} to the Orchestrator profile config15 and the Researcher profile config23. Add the keys to PROTECTED_KEYS in the workspace setup code16, so that existing installs of both profiles get them. The warnings stay at the Hermes defaults (2 identical failures, 3 failures of one tool). A halt at 5 failures instead of 8 costs little: of 348 claim writes, 3 succeeded, so a model that fails 5 times in a row is not about to recover. A halt ends the turn with the Hermes explanation as the final reply24, and the run status is completed2526. The watcher acknowledges the event and does not retry it. But nobody reads the final reply of a wake. Thus add an on_session_end hook to the plugin. When turn_exit_reason is guardrail_halt27, the hook writes a notice that names the Session and the tool. The counters reset at each turn14, so the user's next message starts clean.
  3. A firmer refusal on repeats. The plugin already has a transform_tool_result hook28. Hermes uses the first string that such a hook returns as the tool result29. When the same refusal comes back a second time in one Session, replace its text with a short message: this exact call was refused N times; supply the named fields, or report the problem with ui.notify and end the run. This gives the model a way out before the halt, and it keeps refused results short in the history.
  4. One wake for all champion changes. Today the join key is (kind, subject). Give each wake handler an option to batch by kind, and turn it on for champion.changed only. All pending events of that kind start one Session. Its prompt lists each change, and the end of that Session acknowledges all of them. Events of that kind that arrive while the Session runs wait for the next batch. They do not join the live Session, because a joined event is acknowledged although the running model never saw it. The same option is how any other event kind gets "no concurrent wakes"Q7.
  5. Scenario test. FakePlatform30 starts with champions in leagues of other Coworlds and none in the active Coworld. Make sure that the first tick emits no champion.changed. Then change three leagues of the active Coworld, and make sure that one wake carries all three. With FakeHermesRuns2 and a scripted model that drops summary, make sure that the run halts and ends completed, that its events are acknowledged, and that a notice is written.

Claims stay, and they must work. The wake prompt keeps "record a claim about the new champion". Two pieces of work make claims reliable, and both are outside this ticket:

  • Tool schema. Each multi-action tool has the same weakness as claim: the required fields for each action exist only in descriptions. The Orchestrator has 13 multi-action tools out of 18, and the Researcher has 11 out of 14. If write actions become separate tools, or one tool gets a schema for each action, providers can enforce the required fields. The cost is a longer tool list. That decision has its own Asana task.
  • Tool-call tests across mid-tier models. core/tests/model/test_tool_call_format.py already sends one instruction for each tool to each configured model through OpenRouter. It is skipped without a key, so it stays out of CI. Extend it in three ways. Add a case for each write action with required fields (today the claim case is a search). Pin the provider host, so the same model is tested on different hosts. Add a case where the history already holds one refused call. Then print the first-try valid rate for each model, host and action. This gives the evidence for the schema decision. A variant through a real Hermes gateway can follow if the direct test passes but Sessions still fail.

Removing failed calls from the history. Hermes has no plugin hook that edits the conversation history during a run. A context-engine plugin can do it. Its select_context() may replace the list of messages sent on each request, and the saved transcript does not change31. It could drop refused calls and their results, and leave one note in their place. The cost is real. The context-engine slot is exclusive, so the plugin would have to subclass the built-in Hermes ContextCompressor32, which is not a stable API. Removing messages from the middle also breaks the prompt cache, and cached input costs about a tenth of the full price. Decide after the multi-model tests show whether it helps models recoverQ6.

The other ideas of the task come later. A per-run limit of our own on identical refusals would duplicate the Hermes hard stop. The spend-rate alarm belongs on top of the inference state. It can read usage from the Hermes post_api_request hook.

4 · JAME-175: teach the dispatcher what provider errors mean
  • The dispatcher classifies only errors at run start. On 429, gateway_draining or inference_unavailable, it puts the message back in the queue. Each other start error becomes queued or failed, as its retryable flag tells33.
  • A run that fails partway stores text, not a class. The dispatcher copies the error string of the run onto the admission and marks the admission failed33.
  • Use the Hermes classes, not text matching. Read the class that the plugin hook recorded for the run (Section 2). Use the text only when the hook recorded no class.
  • A failure in the middle of a run should not leave the original message queued. The failed run already made tool calls and wrote records. A replay of the original text would repeat that work and put the user's message in the Session two times. Instead, resume with a continuation prompt after the wait.
  • Model fallback cannot help on a billing error. The GLM fallback uses the same OpenRouter key15. Thus, after a 402, it can only spend the last cents.

Mid-run failures. Today an admission has one of these statuses: queued, running, completed, failed, cancelled or interrupted. This change adds one status, waiting, for an admission whose run failed with a budget or provider class. When the inference state clears, the dispatcher starts a run with a continuation prompt, not the original text. The admission rows of the incident show that such a prompt already comes to the dispatcher as a user message: "Continue my interrupted request from its saved progress. Inspect existing action receipts…". Its source is not in this repository or in the metta workspaces folder. Thus it probably comes from the IDE front end (unverified). The result keeps the user's request alive and does not repeat its side effects.

The 402. The task text says the following, and this report did not check it against the OpenRouter documentation. OpenRouter reserves up to 131,072 output tokens for each request. It refuses the request when the remaining credit cannot pay for that worst case. If this is true, the key looks empty before the $10 is spent, and the fallback model on the same key hits the same wall. A lower output cap would make the last dollar usable. A quick search of the Hermes config defaults found no setting for itQ2.

5 · JAME-174: make research serve aware of the budget
  • The gate checks only expiry. This is true both in research_core17 and in the image34. A key that is spent but not expired leaves the workspace "available".
  • Early renewal will not work as the task writes it. The lease endpoint of the platform gives back the same key while that key is more than the grace period from expiry and is not disabled35. The endpoint never compares the spend of the key with its limit.
  • Early renewal is also not necessary. When the platform mints a key, the limit of the key is the whole account balance35. The balance goes up only at the daily refill36. Thus a spent key means a spent account until the refill. Keys expire at the refill plus a grace period, so the scheduled renewal already brings a new key at that time.
  • The useful part is the state and the gate. Record budget_exhausted with the refill time, and keep new and queued work waiting. Answer 503 inference_unavailable with that time, and clear the state when a new key arrives.
  • The remaining credit is easy to read. The key-info endpoint of OpenRouter, called with the key itself, reports usage and the remaining limit. The lease loop could read it to give a warning before the key reaches its limit.

What the change looks like. It is the inference state from Section 2, applied to the budget:

  1. The lease code in the image writes the next refill time next to the lease file. It gets that time from next_refill_at in a refusal. If no refusal gives it, the time is the expires_at of the lease minus the 10-minute grace period.
  2. The plugin's api_request_error hook writes budget_exhausted, with that refill time, on billing.
  3. inference.available() returns false while budget_exhausted is set. Then the dispatcher, the watcher's wakes and Researcher dispatch all wait.
  4. The image's web app answers 503 inference_unavailable with the reason and the refill time. Thus /ide-next can show "out of budget until 4:00 PM".
  5. The lease code in the image clears the state when it installs a new key. It also schedules its next renewal no later than the refill time. Thus the workspace resumes on time, even if the platform's renew_at is later.
  6. Optional: read the remaining credit at each renewal and every few minutes, and show "about $1 left" as a warning.

Scope across repositories. None of this needs a change in metta. If you later want the platform to refuse a spent key early, lease() would compare the usage of the current key with its limit. That is a small change in the metta lease code35. But it gains nothing until the platform can add money during the day.

Test. Use FakeHermesRuns and fail one run with a billing class. Make sure that the admission becomes waiting with a reason. Make sure that new messages get 503 with the refill time. Make sure that a new lease clears the state and starts a continuation run.

6 · Recommended order and ticket changes
  • First, one change: champion sync for the active Coworld only, champion wakes merged by kind, the hard stop with its notice, and the firmer repeated refusal (JAME-176).
  • Second: the inference state and the gate change (JAME-174).
  • Third: dispatcher classes and continuation resume (JAME-175), on top of that state.
  • At the same time: the tool-call tests across several models, and then the tool-schema decision that they inform.
  • You can unpause workspace 58bda2da at any time. All 14 champion wakes ended completed, so their events are acknowledged, and all 14 leagues now have stored champion rows.

The first change alone would have removed about $5.00 of the $10.02, because none of the 14 wakes would have started. The rest is a normal first session: setup about $3.20, chat about $1.00 and a Researcher about $0.90. That is about half of a day's budget in 27 minutes, which is worth watching separately (see the later items).

Ticket by ticket

  • JAME-176: rescope. The "What to find out" section closes with the answers in this report. The new scope: champion sync reads the active Coworld only, champion wakes merge by kind, the hard stop halts at 5 failures of one tool with a notice, repeated refusals become firmer, and the scenario test. Drop the custom per-run limit, because the Hermes hard stop replaces it. Move the spend-rate alarm to later. The tool-schema question has its own task, "Decide whether to split multi-action research tools so required arguments are enforced". The multi-model tool-call tests also need a ticket.
  • JAME-174: keep, with edits. Replace "renew early after exhaustion" with "renew no later than the refill time". Extend the scope from chat messages to each run start (wakes and Researchers). The shared gate gives this at no cost. Note that this ticket builds the inference state that JAME-175 uses again.
  • JAME-175: keep, with edits. Use the Hermes FailoverReason through the plugin hook, not text matching. Change "leave the message queued" to "hold it as waiting and resume with a continuation prompt". Treat the output-token cap as an open questionQ2, not as a fix.

Later items and what would bring them forward

  • Spend-rate alarm: bring it forward if a loop that the hard stop does not catch ever spends more than a few dollars. An example is a loop that varies its tools.
  • Setup-wake cost: bring it forward if new workspaces usually spend more than a third of the daily budget on setup. This setup wake sent 18.7M input tokens, because each call resent a growing history.
  • Removing failed calls from the history: bring it forward if the multi-model tests show that models recover better with a cleaner historyQ6.
  • Output-token cap: bring it forward when the answer to Q2Q2 finds the setting.
  • Context v1 league check: this check is independent of spend, so you can do it at any time.

Appendix B · Hermes and platform mechanisms referenced
  • Loop guard14. Defaults: warnings_enabled true, hard_stop_enabled false, non_interactive_hard_stop_enabled true. Limits: exact_failure_warn_after 2, exact_failure_block_after 5, same_tool_failure_warn_after 3, same_tool_failure_halt_after 814. The nested config form hard_stop_after: {same_tool_failure: N} sets the halt14. The non-interactive switch applies only to platforms outside {"cli","tui","desktop","acp","subagent","api_server"}14. A result counts as a failure when its first 500 characters contain the quoted key "error" or "failed", or when it starts with Error. The guard's own refusals are exempt14. The block after 5 identical failures resets when a successful write lands between them. The halt for one tool does not reset. The counters reset at each turn14.
  • What a halt produces. The tool round ends the turn with turn_exit_reason = "guardrail_halt" and adds the guard's explanation as the final assistant message24. guardrail_halt is not a failing exit reason, so the turn counts as completed25, and the runs API reports completed26. The on_session_end hook receives turn_exit_reason27.
  • Plugin hooks used here. transform_tool_result can replace the result of a tool before it goes into the history. The first string returned wins29. api_request_error receives session_id, model, provider, status_code, retryable, reason, error {type, message} and the request payload19. No hook edits the history.
  • Context engines. context.engine has a default of compressor11. The select_context() method of an engine runs on each provider request. It can replace the list of request messages, and the saved transcript does not change31.
  • Error classes18. billing is "402 or confirmed credit exhaustion". The other classes include rate_limit, upstream_rate_limit, overloaded, server_error, timeout, context_overflow, payload_too_large, auth, auth_permanent and model_not_found.
  • Gateway concurrency. gateway.api_server.max_concurrent_runs has a default of 1011. Above that number, the runs API answers 429, and the watcher retries at its next tick.
  • Leagues on the platform. GET /v2/leagues lists 501 leagues. Each league carries its Coworld as game.coworld_id, which _league reads22. None belongs to Generals (cow_2660da8b…)7.
  • Platform lease35. It gives back the current key while expires_at is more than the grace period away and the key is not disabled35. When the balance is spent, it answers budget_exhausted, with retry_at set to the next refill35. It mints keys whose limit is the balance and whose expiry is the next refill plus the grace period35. The allowance is $10 each day, with a cap of $5036.
