2 · Hermes in brief
  • Hermes is an open-source Python agent harness from Nous Research. We pin v0.21.5 (tag v2026.9.24). A long-lived gateway process hosts its cron ticker.
  • A profile distribution packages a whole agent as a git repo. Install and update keep the user’s memory, sessions, credentials, and workspace/ untouched.
  • Each tick of a cron agent job is a fresh agent session. A pre-run script can feed the prompt or cancel the model call.
  • Hermes skips a tick while the same job still runs. It has an inactivity watchdog but no hard wall-clock cap.
  • Loop guardrails act inside one turn. Loops across turns and terminal thrash are known gaps. Plugins fire hooks in cron sessions too.
  • Hermes Kanban is a durable SQLite task board on one host. A dispatcher in the gateway claims ready tasks and starts a fresh worker session for each one (§2.12).

This section explains Hermes for a reader who has never used it. We pin v0.21.5, tag v2026.9.24, released 2026-09-24. It is the latest stable release: gh release list shows no newer non-prerelease5. Every fact here was checked against the Hermes source6 and the official docs7. Later sections build on it.

2.1 What Hermes is

Hermes Agent is an open-source agent harness from Nous Research. It uses the MIT license and needs Python 3.11 or later. The first tagged release came in March 2026. The release pace is very fast: hundreds of commits land each day. Hermes is one of the most used agents on OpenRouter.

Hermes runs as several processes:

  • The hermes CLI and its terminal UI, for interactive use.
  • A long-lived gateway daemon. It hosts the messaging adapters, the cron ticker, an optional API server, webhooks, and A2A.
  • hermes mcp serve, an MCP server.

All state lives in a home directory, HERMES_HOME (default ~/.hermes). Profiles give separate homes. The docs warn against two agents that share one home.

Headless runs. hermes -z "<prompt>" or hermes chat --oneshot --query-file runs one prompt with no UI8. Useful flags: --max-turns, -s to preload skills, -t to pick toolsets, --yolo, --provider and --model, and --usage-file. The usage file reports tokens, cost, and turn_exit_reason. Exit codes are 0, 1, and 130.

2.2 Profile distributions: how a Hermes agent is shared

A profile distribution packages a complete agent as a git repo: SOUL, config, skills, cron jobs, MCP connections, and plugins9. Three commands manage it:

  • hermes profile install <git-url or local dir> [--name] [--alias] installs it as a profile.
  • hermes profile update <name> pulls a new version.
  • hermes profile info shows what is installed.

The manifest. distribution.yaml holds name, version, description, hermes_requires, author, license, and env_requires. Each entry in env_requires has a name, a description, a required flag, and a default. The installer checks the required variables and writes a .env.EXAMPLE file.

Who owns which path. The distribution owns some paths, and the user owns others. The manifest’s distribution_owned list can change the defaults.

OwnerDefault pathsOn hermes profile update
DistributionSOUL.md, config.yaml, mcp.json, skills/, cron/jobs.json, distribution.yamlFiles are replaced. Skills merge per entry. cron/jobs.json merges by job id: the local paused or enabled state survives, and newly shipped jobs arrive paused. config.yaml is preserved unless the update uses --force-config.
Usermemories/, sessions/, state.db*, auth.json, .env and other credential stores, logs/, workspace/, plans/, home/, *_cache/, local/Never shipped, never overwritten. The installer hard-excludes these paths even if an author ships them.

The hard exclusion protects the installer, not the author. Thus, the author must still keep these paths out of git with a .gitignore.

Two limits. First, an install does not move runtime data between hosts. Sessions, memory, and cron history need a separate migration10. Second, a distribution cannot pin a git ref yet. The docs plan #v1.2.0-style pins, but install tracks the default branch today.

2.3 How cron works

Cron is the core of this design, so this subsection is the longest.

Definition. Three paths create a cron job11. The CLI is one: hermes cron create "<schedule>" "<prompt>" --skill … --workdir …. The agent’s cronjob_manage tool is another. It is off in cron sessions unless cron.allow_agent_scheduling: true. The REST Jobs API is the third. A schedule can be natural language (“every 10m”), a duration, a 5-field cron expression, or an ISO time for a one-shot job. Definitions live in cron/jobs.json. Output goes to cron/output/<job>/<ts>.md.

One tick, one fresh session. Each tick of an agent job starts a fresh agent session. The job’s skills load, and the prompt runs to completion. Then Hermes delivers the final response, locally or to a chat platform. A response of [SILENT] suppresses delivery.

The job’s workdir. It sets the tools’ working directory, and Hermes loads that directory’s AGENTS.md. It must be an existing absolute path12. Without it, no AGENTS.md loads, and tools run from the gateway’s directory.

Pre-run scripts and wakeAgent. A job can name a pre-run script. Hermes injects the script’s stdout into the prompt. If the script prints {"wakeAgent": false}, Hermes skips the model call for that tick. A no_agent job runs only a script, with a cap of 3600 s. An option, continuity=true, prepends the previous run’s output to the prompt. This design does not use it.

Script rules. Three rules shape our scripts13:

  • A script must resolve inside $HERMES_HOME/scripts/.
  • A Python script runs under Hermes’s own interpreter. A job can pin a user-managed venv with --interpreter.
  • Hermes sanitizes the script environment. Scripts do not inherit provider API credentials. Other secrets reach a script only when the profile’s config.yaml declares them and its .env defines them.
BehaviourWhat Hermes does
TickerRuns every 60 s under a file lock.
OverlapIf a job still runs, Hermes skips its next tick. Two runs of one job never overlap14. This limit applies to one cron job only. Research iterations are Kanban card runs, not cron runs, so several run at the same time up to the configured cap (§6).
Crash safetynext_run_at advances before dispatch, so a crash runs a slot at most once. Hermes force-releases claims older than max(2×interval, cron.inflight_max_minutes).
Missed slotsCatch up once.
Restart mid-runHermes marks the run unknown and does not run it again.

Time limits. Agent jobs have no wall-clock cap. An inactivity watchdog hard-interrupts a job after 600 s with no activity by default15. HERMES_CRON_TIMEOUT sets the limit, and 0 turns it off. A long, silent foreground command can trip the watchdog. agent.run_budget_seconds only injects a soft “wrap up” notice at 80% of the budget. No command cancels a running job16.

Failure handling. A first line of [CRON_FAILURE] marks a run as failed. A streak of 3 failures raises a review nudge. Hermes deduplicates incidents (hermes cron incidents), logs runs (hermes cron runs), and checks health with hermes cron doctor. If the network fails before any model call, Hermes retries at 5, 15, and 30 minutes.

The gateway must run. Cron fires only while the gateway runs. hermes cron tick runs the due jobs once, by hand. How the gateway stays up is a matter for the host, not for this design (§4).

Memory and model in cron. Built-in memory is active in cron sessions, because the scheduler sets skip_memory=False17. The cron AGENTS.md in the Hermes repo says otherwise, but that text is stale18. Hermes picks the model in this order: the job’s pinned model, then cron.model, then the main model. A job with a pinned model never uses fallback providers.

2.4 Long-running sessions

Outside cron, Hermes keeps one session alive for a long time. Sessions live in state.db and can resume. Context compression is on by default. /heartbeat and /loop re-prompt the same session, and /goal keeps an objective across turns19. Cron is the opposite: a fresh session per tick.

Hermes also runs subagents through delegate_task, with monitors for stale heartbeats20. It supports background terminal processes. Health checks: hermes cron status and the API’s /health.

2.5 Loop guardrails inside a turn

tool_loop_guardrails watches tool calls inside one turn21:

A successful write, a patch, or a green terminal run resets the counters. A halt ends the turn, not the session. Hard stops are on by default only for non-interactive platforms: the gateway and cron22. hermes -z and --oneshot count as “cli”. There, the guardrails only warn unless hard_stop_enabled: true23.

Other limits: agent.max_turns defaults to unlimited in code, but the docs say 50024. A repetition guard stops degenerate repeated output. Hermes has no hard token or USD budget, and it reports usage after the fact.

Three gaps are open issues. Loops that span turns escape the detectors25. Terminal thrash escapes them too26. So do loops spread across sibling tools27.

2.6 Skills

A skill is a directory with a SKILL.md file and YAML frontmatter that names name and description28. The format follows the agentskills.io standard. Optional references/, templates/, scripts/, and assets/ folders load progressively. Hermes reads skills from these sources, in order of precedence:

  1. The project’s .hermes/skills or .agents/skills, after hermes skills trust. Hermes scans their content.
  2. The profile’s own skills/. A distribution ships its skills here.
  3. skills.create_dir.
  4. skills.external_dirs.

The agent can create and patch skills with skill_manage. A background review nudges it to write memory and skills. A curator archives skills unused for 30 days, but it skips pinned and cron-referenced skills29. Our agentskills.io SKILL.md directories work as they are.

2.7 Memory

Built-in memory is two files in the profile’s memories/: MEMORY.md and USER.md30. §7 describes them in detail and recommends how we use them. session_search searches past sessions in state.db. It is its own toolset, independent of the memory switches31.

2.8 Tools, approvals, and safety

Terminal backends include local, docker, ssh, and modal. Other tools: file, web, browser, execute_code, and background processes. Hermes is also an MCP client (mcp_servers:). Toolsets are set per platform, and “cron” is one platform.

Approvals use approvals.mode: smart, manual, or off32. In cron, cron_mode defaults to deny. Unattended runs use approvals.mode: off or --yolo. A hardline blocklist and the approvals.deny globs still apply. HERMES_WRITE_SAFE_ROOT confines file writes to one directory tree. Two bugs at the approval boundary are open3334.

2.9 Plugins and hooks

A Python plugin registers hooks35. The hooks fire in CLI, gateway, and cron sessions, because cron loads plugins36. The main hooks:

  • pre_tool_call: a policy hook. It can block a tool call. It fails closed on timeout.
  • post_tool_call: an observer. It sees the tool, the arguments, the status, and the error type.
  • on_session_start and on_session_end. Both are observers, and Hermes ignores their return values. The end hook reports completed, failed, or interrupted, and turn_exit_reason.
  • pre_llm_call: it runs once per turn, before the model call. Hermes adds its returned text to the user message.
  • post_llm_call, and more.

The callback timeout defaults to 30 s. Gateway event hooks are different, and they do not run in cron.

Where plugins live. A profile’s own plugins sit in its plugins/ directory, as user plugins37. Project-local plugins in .hermes/plugins/ load only when HERMES_ENABLE_PROJECT_PLUGINS=true.

2.12 Kanban: the task board

Hermes Kanban is a durable task board in SQLite (~/.hermes/kanban.db)42. It is single-host by design. The docs put a board shared across hosts out of scope. Named boards give hard isolation: each board has its own database, workspaces directory, and dispatcher pass.

Tasks. A task has these parts:

  • A title, a body, and one assignee, which is a profile name.
  • A status: triage, todo, ready, running, blocked, review, done, or archived.
  • Options: an integer priority, an idempotency key, a start time (scheduled_at), a model and skills for this task only, and goal mode.
  • Links from parent to child, comments, and attachments.
  • Runs: one row per attempt, with the outcome and a structured handoff (summary plus metadata).

The dispatcher. By default, the dispatcher runs inside the gateway every 60 s (kanban.dispatch_in_gateway, dispatch_interval_seconds). Each pass reclaims stale or crashed claims, promotes ready tasks, and claims a task atomically. It then starts the assignee profile as a worker (hermes -p <assignee> chat -q …) in the task’s workspace43. Two settings cap the work in flight: kanban.max_in_progress for the board and kanban.max_in_progress_per_profile for each profile. The dispatcher takes ready tasks in priority order, highest first, then oldest first42.

Workspaces. Each task names a workspace kind:

  • scratch: a temporary directory. Hermes deletes it when the task completes.
  • dir:<path>: an existing absolute directory. Hermes keeps it.
  • worktree: a git worktree per task. Hermes keeps it.

The worker lifecycle. Hermes injects the lifecycle into the worker’s prompt. The worker calls kanban_show, does the work, and calls kanban_heartbeat during long steps. It ends with exactly one of kanban_complete(summary, metadata), kanban_request_review, or kanban_block44. Hermes protects this lifecycle in several ways:

EventWhat Hermes does
The worker tries to stop without a final board callUp to two nudges remind it to complete, request review, or block.
Repeated protocol violationsA bounded retry, then an automatic block.
Rate limit or provider overload (exit 75)Requeue, with no failure counted.
Bad credentials or a bad model (exit 78)Block at once, after one attempt.
No heartbeat in the last hour of a run older than 4 hStale reclaim: the task goes back to ready.
Repeated spawn failures on one taskThe kanban.failure_limit circuit breaker blocks it (default 2).

Interfaces. Agents use tools: kanban_show, kanban_list, kanban_complete, kanban_block, kanban_heartbeat, kanban_comment, kanban_create, kanban_link, kanban_unblock, and more. Humans and scripts use the CLI: hermes kanban init, create, list, watch, stats, dispatch --dry-run, and more. create --idempotency-key makes a retried create return the same task.

Plugin hooks. Three hooks fire after the database change commits. kanban_task_claimed fires in the dispatcher. kanban_task_completed and kanban_task_blocked fire in the worker.

Orchestration features. Kanban also offers features that route and judge work:

  • An automatic decomposer for triage tasks (kanban.auto_decompose, default true).
  • A review lane (kanban.review_dispatch, default true).
  • Goal-mode cards, a swarm and blackboard helper, and a respawn guard.

4.1 Consequences Approved by default

Research state is portable by design. All research state lives in the workspace git repo. Hermes runtime data is convenience, not truth: sessions in state.db, cron history, the Kanban board, and built-in memory. Thus, a move between hosts needs only the workspace, plus the credentials. The board does not travel with the profile, but the planner rebuilds the queue from the workspace (§5.1). queue-keeper always pushes the workspace to AUTORESEARCH_WORKSPACE_REMOTE after each commit Decided · Oct 7. Thus a migration, a restore, or a shared copy is a clone.

Sleep and wake. A host can pause the agent. Cron and the Kanban dispatcher then stop. On wake, Hermes catches up a missed slot once. XP requests keep running on Softmax’s side, and xp-poll collects them later. No design change is needed.

Self-bootstrap. A hosted environment does not always offer a shell. Thus, the first queue-keeper run sets up everything, and every later run repeats it safely (it is idempotent). It does these steps:

  1. Seed the workspace from games/$AUTORESEARCH_GAME/seed/.
  2. Run git init.
  3. Create the venv.
  4. Create the profile’s Kanban board (§5.1).
  5. Check the credential.

The installer then has two manual steps only. Fill in .env. Then resume the shipped cron jobs, which arrive paused.

5.3 One card run Approved by default

A card run is one iteration. It follows these steps:

  1. Create. A script, the planner, or an iteration creates a Pending card through the queue create tool. Scripts use idempotency keys.
  2. Claim. On each pass, the dispatcher checks the cap of two Claimed cards. Under the cap, it claims the ready card with the highest Kanban priority atomically (§5.1). System Design §5.1 and its card priorities give the order.
  3. Start. The dispatcher starts a fresh worker session in the card’s worktree, branched from the main workspace.
  4. Brief. The worker reads its card with kanban_show. The card body names its briefing, .supervisor/briefings/<card-id>.md. System Design §5.1 defines the content.
  5. Work. The worker does the card’s one unit of work in its worktree. It changes only the entities that its card names, and it creates new entities freely.
  6. Complete. The worker writes its journal entry with Decisions, the acknowledgements, valid records, and any follow-up cards. It then calls kanban_complete with the outcome and the journal ref in the metadata. An XP launch also ends the run, and xp-poll later creates the review card. A launch that the platform refuses for lack of credits completes with outcome partial.
  7. Validate. The plugin’s kanban_task_completed hook checks the handoff in the worktree (§5.4).
  8. Merge. queue-keeper merges the validated worktree into the main workspace, regenerates the generated files, commits, and recomputes the signals.

The per-card briefing Approved by default. queue-keeper builds one briefing for each Pending card, at .supervisor/briefings/<card-id>.md. It rebuilds the file on each run, so the briefing is current at the claim. The content follows System Design §5.1: a short shared part, the card’s own slice, and, for planning cards, the open proposals and plan.md.

Approved by default As an alternative, the plugin’s pre_llm_call hook injects the briefing on the first turn35. The on_session_start hook cannot do this, because Hermes ignores its return value.

5.4 Validation, merge, and the promotion lock Approved by default

Two iterations change the same research state at the same time. These rules keep the main workspace consistent. System Design §3.7, “Concurrent iterations” defines the research-side rules.

  • Handoff validation at card completion. Our plugin’s kanban_task_completed hook checks the worktree. It needs a journal entry with Decisions and doctrine_version, an acknowledgement per delivered inbound message, valid records, and valid follow-up cards. A card from an inbound task also needs the acknowledgement to its sender. System Design §5.8, “Card completion” defines the handoff. The hook also counts doctrine violations (§5.9).
  • Merge one at a time. queue-keeper merges only validated worktrees, one merge at a time. For an invalid worktree, it creates a repair card instead.
  • Generated files. queue-keeper regenerates kb/index.md, backlinks, and contradiction lists after each merge. Iterations never edit them.
  • Reconciliation cards. A merge conflict creates a reconciliation card. Hermes documents this pattern: a neutral reconciler resolves the conflict, with the bundled agent-merge-conflict-arbiter skill57. Neither colliding worker judges its own conflict.
  • STRATEGY.md promotion lock. A lock file in the main workspace, plus a check in the submit tool. Only one promotion runs at a time. If the champion changed during the evaluation, the promotion card creates a re-evaluation card instead (System Design §5.5).
  • IDs without coordination. Every entity ID is a type prefix plus a ULID (System Design, ID format). records new creates each ID and validates its format. Concurrent iterations need no ID allocator.

5.6 Fallback if Kanban misbehaves Approved by default

If Kanban misbehaves before Friday, we have two fallbacks:

  2. Switch to one serial cron agent job that claims the top Pending card itself. The same card format then lives in a plain file queue in the workspace.

The research data model does not change in either case. The Wednesday go/no-go (§14) chooses between Kanban and the serial fallback.

5.7 Why a fresh session per iteration

Kanban makes this native: each card run is a fresh worker session. Teams that run agents for long periods keep state on disk. The Ralph loop58, Karpathy’s autoresearch59, Anthropic’s guidance on long-running harnesses60, and OpenAI’s guidance on long-horizon Codex tasks61 all do this. Fresh sessions prevent the loss of detail from compaction across days. They make crash recovery trivial, and they give each iteration a budget. They also give inbound messages a clean boundary to land on. The research method that fills each session is in System Design §2.

Thus, we do not use Hermes /loop, /heartbeat, /goal, continuity=true, or Kanban goal mode for the main loop. Compaction loss over days, hidden state, and harder stuck detection rule them out (Appendix C).

7.1 What it is

The Hermes docs describe built-in memory as follows30:

  • Two files in the profile’s memories/. MEMORY.md holds the agent’s notes: 2,200 characters, about 800 tokens. USER.md holds a user profile: 1,375 characters, about 500 tokens.
  • A frozen snapshot. Hermes injects both files into the system prompt at session start. A write during a session reaches the disk at once, but it shows up only in the next session.
  • The memory tool. The agent curates the files with add, replace, and remove. There is no auto-compaction: a write over the limit fails, and the agent must consolidate. Hermes rejects exact duplicates. It also scans entries for prompt-injection and exfiltration patterns.
  • Approval. write_approval: true stages writes for a human to approve with /memory pending. The default is false.
  • Background review. A background self-improvement review can also write memory. Cron runs skip it (skip_background_review=True)17.
  • Ownership. Memory is per profile and user-owned. A distribution never ships it, and an install never moves it9.
  • session_search is separate. It searches all past sessions in state.db with FTS5, at no LLM cost. It is its own toolset31.

7.2 What it gets us

  • Operating notes in every fresh session, at near-zero effort. These are harness and tool gotchas. Two examples: “the XP CLI needs --mine when no player is active” and “long builds must run in the background”. Without memory, a fresh session re-learns them from the workspace or by failure.
  • “Did I already try this?” recall. session_search covers past iteration transcripts. co-gas mined past agent sessions for abandoned ideas for the same reason.

7.3 What it imposes

  • A second memory outside the workspace git repo. It has no IDs, no provenance, and no history. The Preston-role agent cannot see it through comms/ refs. It can contradict the claims in kb/ and lessons.md.
  • It does not move with the research state between hosts (Rohit’s note on runtime data10).
  • Cost. About 800 tokens in every session’s prompt, plus curation work when the file fills up.
  • USER.md has no use. No human converses with this agent.
  • No approval is possible. With write_approval: true, nobody approves writes in an autonomous loop. It must stay false.
  • One file for concurrent workers. Up to two workers run at once in one profile, so both see and can write the same MEMORY.md.

9.1 Principles

  • Written for Preston Decided. Outbound message bodies are written for the Preston-role agent. Preston rephrases them for its human.
  • Preston carries the human’s authority Decided. The human never connects to the research system directly. Every message, steer, and task from the Preston-role agent carries the human’s full authority. Messages have no on_behalf_of field (System Design §7, Inbound).
  • One consumer now, several possible Decided. v0 assumes one consumer, the Preston-role agent. Each consumer keeps its own seq cursor, and the system records seen per consumer. Thus, nothing locks out more consumers.
  • Read-anything assumption (James). The Preston-role agent can retrieve any internal representation. Thus, the transport does not mirror the workspace. It carries direct messages and questions, plus pointers into the workspace.
  • Mailbox, not conversation. The system writes whether or not anyone listens, and it never waits for a reader. Messages persist, and readers catch up with a cursor.
  • Start simple. v0 builds the canonical file store and a CLI and Python library. A network adapter comes only after the Preston channel is known.
  • Hosting separation (Rohit’s rule10). Adapters never use host-specific authentication or domains. Every endpoint and key comes from configuration.
  • Single writer per side. Only the system writes comms/outbox/. Only external agents write comms/inbox/.

Two writers on the system side produce outbound messages. The research agent sends through the communicate skill and autoresearch comms send. The system’s scripts, queue-keeper and health, send with from: runtime.

9.2 Storage and delivery

  • Outbox. Each message is one immutable JSON file at comms/outbox/<seq>-<id>.json. The writer gives it a temporary name and then renames it, so a reader never sees half a file.
  • Inbox. Each inbound message is one JSON file at comms/inbox/<id>.json. The four inbound kinds are reply, steer, seen, and task (System Design §7, Inbound). queue-keeper puts each unprocessed message into briefings as System Design §5.1 says. Urgent messages go into every briefing. Other messages go into the briefings of cards on the same thread.
  • Inbound tasks Approved by default. An external service, for example the IDE through a comms adapter, requests work with an inbound task. Its fields are title, mode, why, refs, and priority. queue-keeper validates the message and creates a card. The card’s created_by is the inbound message id, and its idempotency key is task:<inbound id>. The external service never writes the board. The agent acknowledges the task when its card completes.
  • Seen Decided. The Preston-role agent or its adapter sends seen with message ids to mark them read. queue-keeper uses it to tell unread messages from unanswered ones when it escalates.
  • Cursor delivery. Readers poll by seq cursor (“everything after N”). Each consumer keeps its own cursor. Delivery is at-least-once, and the ids make re-reads idempotent.
  • Inbound latency. Normally the next card run that starts. For a steer with urgency: now or a valid task, queue-keeper creates a card within about a minute (§5.2). The card runs when a slot is free.
  • No synchronous answers Decided. The research loop never answers synchronously. The Preston-role agent answers the human’s questions at once by reading the workspace. The loop answers inbound messages at a later card run.
  • Late answers Decided. A reply that arrives after its question expired, or after the system moved on, is still delivered. The research agent sees it and decides what to do. It can discard a stale answer and acknowledge it as noted.
  • Retention. Everything stays in git.
  • Derived status. Nobody edits a message. The reader library computes each message’s status from later messages (System Design §7).

A resolver, autoresearch comms resolve <uri> [--rev], maps an ar:// URI to its workspace path and content. The URI form matches MCP resource URIs. As a result, an MCP adapter can expose every ref directly as an MCP resource. Whether rev alone keeps refs stable is still open (§9.5, question 3).

Appendix C · Alternatives considered
  • New in revision 5: the single serial cron agent job is now the fallback, and Kanban’s orchestration features stay unused.
  • Revision 4 added five alternatives. The most important is a plain project repo instead of a profile distribution.
  • Revision 3’s supervisor fallback driver is dropped, and so is its EC2 host design.
  • The alternatives that revisions 1 to 3 rejected stay rejected.

New in revision 6

At most one evaluation in flight, enforced by softmax xp create. Removed. System Design allows several evaluations at once. A credit refusal pauses one evaluation as awaiting-credits.

One planning card always Pending. Replaced by planning cards on a fixed schedule, plus one when the queue-growth signal fires.

A shared ID allocator. Replaced by ULIDs, which need no coordination.

One general briefing for every card. Replaced by a briefing per card. The general briefing carried much that was irrelevant to one card.

Priority through todo or scheduled_at. Not needed. Kanban has a priority field that sets the claim order (§5.1).

New in revision 5

One serial research-iteration cron agent job, as in revision 4. Superseded by the Kanban dispatcher Decided. It runs one iteration at a time and keeps next actions in plan.md. It stays as the fallback (§5.6).

Kanban’s orchestration features: the decomposer, the review lane, goal mode, links, and the swarm helper. Not used. They route and judge work on the board, so the board starts to hold research state. The board stays a pure next-action queue (§5.1).

New in revision 4

A plain project repo with project-local .hermes/skills and .hermes/plugins, instead of a profile distribution. Rejected. Project plugins need HERMES_ENABLE_PROJECT_PLUGINS=true37. Cron scripts must live in the profile’s scripts/13. And distributions are Hermes’s supported path to share an agent9.

A hard wall-clock cap through a systemd fallback driver. Dropped. James accepts no hard limit for v0. The driver also assumes a host that we do not control.

Built-in memory fully off (revision 3) or fully on. §7 compares both with the minimal recommendation. With memory off, the agent relies on lessons.md plus session_search. System Design specifies a tiny MEMORY.md, so these options stay for comparison only.

Install the Codex CLI only for the compiler. Rejected. The compiler runs on Hermes (§11).

Keep revision 3’s EC2 host design. Removed. Hosting is invisible to this design (§4).

Carried over from revision 3

A Python supervisor daemon plus hermes -z per iteration, as the primary driver. The Hermes research itself recommended this. It gives hard timeouts and exit codes. But the team chose Hermes cron as the architecture. Cron gives fresh sessions, no overlap, run history, incidents, and a Jobs API for free. Revision 3 kept this driver as a fallback. Revision 4 drops that fallback too.

Several agent cron jobs, one per role (researcher, compiler, scout). Rejected for v0. Two agent jobs can then write research state at the same time. Revision 5 allows two concurrent iterations of one agent instead, each in its own worktree, with one writer per entity.

One long Hermes session with /loop, /heartbeat, /goal, or continuity=true. The reasons are the same as for revision 1’s rejected long Codex session: compaction loss over days, hidden state, and harder stuck detection.

The Hermes messaging gateway as the canonical comms channel. It ties the contract to one transport. comms/ stays canonical, and Hermes features become adapters.

A Docker container (the revision 1 and 2 packaging). Replaced by the profile distribution.

The Codex CLI harness (revisions 1 and 2). The team replaced it with Hermes.

Carried over from revision 2

  • Our own proto-Preston. An external agent fills the Preston role, and its channel is unknown. A design here fixes choices that belong to others.
  • A2A, MCP, or AG-UI as the core contract. A2A is client-initiated tasks, but our system starts the communication. MCP assumes a connected client session, but the system writes when nobody is connected. AG-UI is a live event stream for front ends. MCP and A2A stay as likely adapters (§9.3, §9.4).
  • Mirror the workspace in the messages. Rejected because of the read-anything assumption. Pointers plus rev are smaller, and they never go stale.
  • A rich inbound command vocabulary. Inbound is only reply, steer, seen, and task. A task becomes a card only after queue-keeper validates it. Thus, the research system stays the only writer of its state.

  • A Python state machine that calls the agent for sub-tasks. It fixes one research method in code, and it needs the most code before Thursday. Its useful part, the list of next actions, lives on as the work queue (§5.1).
