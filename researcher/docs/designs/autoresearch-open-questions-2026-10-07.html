Autoresearch: Open Questions

Questions the design cannot answer alone. Each section explains one question in plain English: the background, why it matters, what the answer depends on, the options, and a suggested starting point. Details are in the Runtime design and the System Design.

Historical record This document records the autoresearch harness in Metta-AI/ide-mvp. The native-Kanban researcher and orchestrator in this repository supersede it, so its paths, commands, environment variables and mechanisms (for example the comms inbox and outbox, the queue-keeper and other cron jobs, spend management) may no longer exist. For the current design, see orchestrator-implementation-notes.md.

1 · How will Preston connect to the research system?

Background. Preston is the assistant that talks with the user in the IDE. It is not part of our system. It reads our system's files and sends it messages. We have built the message format and a simple file-and-command-line connection. We have not built a network connection, because we do not know which kind Preston needs.

Why it matters. We can only build one network connection by Friday. If we pick the wrong kind, Preston cannot talk to the research system at all.

What the answer depends on. Who builds Preston and where it runs. If Preston runs on the same machine, plain files can be enough. If it runs elsewhere, it needs a network connection. It also depends on whether the IDE talks to our system directly or through the Softmax backend.

Options.

  • WebSockets (a live, two-way connection)
  • Webhooks (each side calls a web address when something happens)
  • A2A (a standard protocol for agents talking to agents, which Hermes supports)
  • MCP (a standard protocol for giving an agent tools and data)

Suggested starting point. Ask whoever builds Preston which one they already use, and match it.

Who. James and Rohit, with Aaron

2 · Does Preston need to be told about new messages, or will it check for them?

Background. The research system writes messages (findings, questions, help requests) into an outbox. Each message has a running number, so a reader can ask for everything after the last number it saw.

Why it matters. If Preston only checks when a user opens the page, a help request can sit unread for hours. If Preston must hear at once, we need a notification path, and that is more work.

What the answer depends on. How quickly a human must see a help request, and whether Preston is always running or only starts when a user opens the IDE.

Options.

  • Preston checks for new messages (simplest)
  • We notify Preston when a message arrives (more work, faster)

Suggested starting point. Start with checking. Add notifications only for help requests if users miss them.

Who. James and Rohit

3 · Is a pointer to a saved version enough, or must messages carry copies?

Background. Messages do not copy the research notes they talk about. They point at them, and each pointer says which saved version of the workspace it means (a git commit). Notes change later, so the pointer lets Preston see the note as it was when the message was written.

Why it matters. This works only if Preston's connection can fetch an old version of a note. If it cannot, Preston sees the current note, and that note can say something different from what the message meant.

What the answer depends on. Whether every connection we build can serve old versions from git. Our own command-line tool can.

Options.

  • Pointers only. Every connection must serve old versions (smaller, and our suggestion)
  • Messages also carry a short copy of the relevant text (works everywhere, bigger and repetitive)

Suggested starting point. Pointers only.

Who. James and Rohit

4 · What do we promise when the message format changes?

Background. The research system writes messages in a defined format (version 0). Preston's connection reads them. The format will change as we learn.

Why it matters. Without a promise, any change can break Preston's connection without warning.

What the answer depends on. How often each side can be updated, and who maintains Preston's connection.

Options.

  • Within version 0 we only add things (new optional fields, new message types), and readers ignore what they do not know. Anything that removes or renames a field becomes version 1, and both sides update together.
  • No promise. Update both sides each time

Suggested starting point. The first option.

Who. James and Rohit

5 · Where does the workspace backup live, and how does the machine get permission to push to it?

Background. All research results live in one git repository, the workspace. We decided that it always pushes to a remote copy after every change. That copy is the backup, the way to move to another machine, and the way to share results.

Why it matters. Without a remote and push permission, the system has no backup. A lost machine loses all research.

What the answer depends on. Where the system runs (Nous hosting or our machine), who owns the remote repository, and how secrets reach the machine. Also how large the workspace gets: game replays are big files, and git handles big files poorly.

Options.

  • A private GitHub repository per user, with a key that can only push to that repository
  • Another git host Rohit prefers

Suggested starting point. One private GitHub repository per user. Keep replays out of git and store only their fingerprints and download links.

Who. Rohit, with James

6 · Can the system request evaluation games with only a Player login?

Background. The system acts as one Softmax Player. Uploads and submissions belong to the Player. Our earlier tools found that evaluation-game requests (XP requests) belong to the user account, not the Player. A Player login was not able to read them.

Why it matters. If that is still true, the system cannot run its experiments with only a Player login, and the identity design must change.

What the answer depends on. How the current Softmax platform assigns ownership of XP requests. This is a quick test, not a debate.

Options.

  • Player login works for everything (no change)
  • The system also needs a user login, limited to XP requests

Suggested starting point. Test it first thing. If it fails, ask the platform owners for a Player-scoped way to request XP.

Who. James (test), Rohit (if it fails)

7 · Who keeps the Player login fresh while the system runs for days?

Background. A Player login token lasts about a day. The research system runs for days. Our forum agent lost its access for five days when its login went stale.

Why it matters. When the token expires, the system stops working until someone notices.

What the answer depends on. The hosting choice and whether Softmax offers long-lived tokens for automated players.

Options.

  • The host refreshes the token automatically
  • Softmax issues a long-lived token for automated players
  • A human refreshes it when the system asks for help

Suggested starting point. Automatic refresh by the host. The system already checks the token every minute and asks for help when it is about to expire.

Who. Rohit

8 · Which AI model does the system use, and what are the backups?

Background. The system's thinking runs on a model reached through OpenRouter. If the main model fails or is overloaded, Hermes can switch to backup models, but only if we list them.

Why it matters. The model sets both the quality of the research and the cost. Spending limits are enforced outside the system (Rohit).

What the answer depends on. Budget, what OpenRouter access Rohit sets up, and how well each model works inside Hermes. That last one is untested.

Options.

  • A strong OpenAI model first (Hermes and similar tools are tuned for them), with one or two backups
  • A cheaper model, with a stronger one only for hard steps

Suggested starting point. A strong model first, plus one backup. Compare models once the baseline runs.

Who. James and Rohit

9 · Which league does the system compete in?

Background. The goal for this week is a policy in the top half of the Gods of the Arena leaderboard. Submissions go to a specific league, and the system needs its id.

Why it matters. The wrong league means the result does not count toward the goal.

What the answer depends on. Which leaderboard counts as 'the' GotA leaderboard for the baseline.

Options.

  • The GotA Competition league
  • Another league

Suggested starting point. The GotA Competition league, if that is the one the team watches.

Who. James and Rohit

10 · Where does the research system's repository live?

Background. The autoresearch folder will become a Hermes 'profile distribution': a git repository that Hermes installs with one command. Today it is a folder inside the ide-mvp repository.

Why it matters. Hermes installs a distribution from a repository address. A separate repository is the cleanest way to install, tag versions, and update.

What the answer depends on. Whether the team wants the IDE parts and the research system in one repository or two.

Options.

  • Its own repository, for example Metta-AI/autoresearch
  • Stay inside ide-mvp and install from the folder

Suggested starting point. Its own repository once the first version works. Stay in ide-mvp until then.

Who. James, with Rohit

11 · How do we bring the Paintbot compiler code into the project?

Background. The system turns a written strategy into game code with a compiler that James built for another game (Paintbot). That code sits on an unmerged branch with about 8 commits that were never pushed.

Why it matters. Copying code from an unmerged branch makes its history hard to trace.

What the answer depends on. Whether the Paintbot branch is ready for review.

Options.

  • Push and merge the Paintbot branch first, then copy from main
  • Copy from a fixed commit and note it

Suggested starting point. Copy from a fixed commit now, and record which one. Merge the branch when convenient.

Who. James

12 · How long can one research step run?

Background. Each research step (one work card) is one AI session. We decided that there is no hard time limit. Hermes can still cap the number of actions in a session and can send a soft 'wrap up' reminder.

Why it matters. Without any cap, a confused session can spend a lot of money before the stuck-detection notices.

What the answer depends on. Cost tolerance, and how long real steps take once we can measure them.

Options.

  • A cap on actions per session (for example 150) plus a soft reminder at 45 minutes
  • No cap at first. Measure, then set one

Suggested starting point. Set a generous action cap and the reminder, then adjust from real data.

Who. James and Rohit

13 · When two research steps finish, how are their changes combined?

Background. Up to two steps run at the same time, each in its own copy of the workspace. When a step ends, its changes go back into the main copy, one at a time.

Why it matters. The method decides how readable the history is and how often conflicts happen.

What the answer depends on. Whether the team values a straight-line history (easier to read) or an exact record of each step (easier to trace).

Options.

  • Replay each step's changes on top of the main copy (straight-line history)
  • Merge each step as a unit (exact record)

Suggested starting point. Merge each step as a unit. The record of which step changed what matters more here than a tidy history.

Who. James

14 · Does the work-queue database need a backup?

Background. The list of pending work cards lives in a small database inside Hermes, not in the workspace. It does not travel when the system moves to another machine. The planning step can rebuild the list from the workspace.

Why it matters. A backup avoids a gap after a crash, but it adds one more thing to maintain.

What the answer depends on. How well the rebuild works in practice.

Options.

  • No backup. Rebuild the list when needed
  • Back it up with the rest of the machine

Suggested starting point. No backup. Test the rebuild.

Who. Rohit

15 · What is the minimum number of games before the system can promote a new policy in GotA?

Background. Before the system replaces its league champion, it must win a fair comparison over enough games. The number of games is calculated from how noisy the game results are, but each game also needs a floor that the calculation can never go below.

Why it matters. Without a floor, the system can promote on too little evidence early on, before it has measured the noise.

What the answer depends on. How noisy GotA results are. For reference, one earlier promotion by another team's research loop used 88 paired games.

Options.

  • A fixed floor such as 40 games per side
  • Measure the noise from league data first, then set the floor

Suggested starting point. Start with 40 per side and adjust once the noise is measured.

Who. James

16 · What happens to a message from Preston that matches no current work?

Background. Each work step sees only urgent messages and messages about its own work. A non-urgent reply or instruction about something nobody is working on has no defined path. The same is true for a malformed request to create new work.

Why it matters. Such a message can wait unseen, and the user thinks the system ignored it.

What the answer depends on. How often this happens. That is unknown until Preston exists.

Options.

  • Turn every such message into a work card
  • Give it to the next planning step
  • Reject a malformed request with a reply that explains why

Suggested starting point. Give loose messages to the next planning step (it runs every 2 hours), and reject malformed requests with an explanation.

Who. James and Rohit
