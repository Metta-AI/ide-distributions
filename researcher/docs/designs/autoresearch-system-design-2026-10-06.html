Scope rule for this document This document describes the research agent independent of any harness. It makes three runtime assumptions only. (1) The agent works in iterations. An iteration is one card run: a fresh session that does one card from the work queue. It has no memory except the workspace and its card. Up to 2 iterations run at the same time in v0. (2) Something outside the agent, “the runtime”, starts each iteration with its card and a briefing built for that card. The runtime also checks each card completion, computes signals, and merges and commits the workspace. (3) Tools are command-line programs. The companion document explains how the runtime does this, including how it implements the work queue.

Executive Summary

The system is an autonomous researcher. It improves policies for one game under one Softmax Player identity, for days, with no human approval. The first game is Gods of the Arena (GotA). The agent requests XP, uploads policies, and submits them itself. It notices when it is stuck and asks a human for help. It takes steering from a human through an agent in the Preston role. Success for v0 is a policy in the top half of the GotA leaderboard.

The design gives one agent simple tools and a workspace, not a fixed cognitive architecture. The agent’s records are structured: an ontology of 13 entity types, each with a stable ID and provenance. Topics name what to work on. Pre-registered experiments produce Results. A promotion needs a measured improvement that passes guardrails calibrated from measured metric noise. Knowledge lives in atomic claim files that a linter grades by source tier, with hub pages that cite them. A work queue of next-action cards drives the work. Up to 2 iterations run at the same time, each on one card in its own git worktree, with a briefing built for that card. Doctrine rules and short procedures tie the parts together. Thus, the runtime can measure progress, provenance, and stuckness from the records alone.

1 · Purpose and success

  • An autonomous researcher improves policies for one game under one Player identity, for days, with no human approval.
  • Success for v0: a policy in the top half of the GotA leaderboard. Fallback: a policy that plays reasonably.
  • One serial agent does all the work. Roles split later only where a natural split appears.
  • Up to 2 iterations of this agent run at the same time in v0. Each iteration runs one card from the work queue.

The system is an autonomous researcher. It improves policies for one game under one Softmax Player identity, for days, without human approval1. The first game is Gods of the Arena (GotA).

The agent requests XP, which are hosted evaluation episodes. It also uploads policies and submits them itself. Uploads and submissions are unlimited. The Player’s credits limit XP.

The agent must notice when it is stuck and ask a human for help. It must also take steering from a human, through an agent in the “Preston” role.

Success for v0 is a policy in the top half of the GotA leaderboard. The fallback is a policy that plays reasonably. The run becomes a baseline for later model comparisons.

Design stance · Oct 5 meeting

Start with one serial agent that researches, compiles, and practices itself. Split roles later only where a natural split appears2. Give the agent simple primitive tools and a workspace, not a prescribed cognitive architecture. But make its records structured enough to measure progress, provenance, and stuckness.

Concurrency keeps this stance. Up to 2 iterations of the one agent run at the same time, each on its own card and worktree. See §3.7.

2 · The research method at a glance

  • The research cycle is a loop of entities, not of runtime steps. Evidence feeds investigation, investigation feeds experiments, and experiments produce new evidence and Results.
  • Topics say what to work on. They feed investigation and set the metrics and guardrails for experiments.
  • Five working modes: investigation, scouting, experimentation, maintenance, and planning. Each iteration claims one card, does its one bounded unit of work, then completes the card.
  • The work queue sits outside the cycle. Its cards only point at the entities in the cycle.

Five working modes

The agent works in five modes. Investigation, experimentation, and maintenance come from the “Loop types” task3. Scouting and planning complete the set.

ModeQuestionWhat it doesProcedure
Investigation“Why am I losing?”Diagnose from evidence. Produce claims and hypotheses.5.2
ScoutingWhat do opponents and the league do?Profile opponents and watch the league. Write opponent hubs and claims. Store league snapshots as evidence.5.3
Experimentation“Which change fixes it?”Test one hypothesis with one strategy change.5.4, 5.5
MaintenanceIs the knowledge base honest?Run the knowledge-base linter pass. Consolidate lessons.5.6

Each iteration does one bounded unit of work in one mode, then hands off. That unit is one card from the work queue, and the card names the mode.

3 · Ontology: the entities the agent reasons with

  • 13 entity types. Each has a stable ID and its own file or anchored entry, so messages, other entities, and humans can point at it.
  • Prose describes the present. Records keep the history. A contradicted claim is closed, not deleted.
  • Every judgement cites the evidence or Result behind it. Every claim carries the game versions it is valid for.

The design draws on five sources:

  • PlayerADE pipeline entities: Topic → Hypothesis → Experiment → Result, with stored judgement states4.
  • co-gas candidate records: environment capture, typed evidence, and a pre-registered decision5.
  • optimizer-seed: lessons, closed levers, and the version log67.
  • The Oct 5 meeting: episodic, semantic, and procedural memory with provenance, and knowledge versus beliefs2.
  • The PW compiler: component status and build provenance8.

Principles

  • Stable IDs. Every entity has a stable ID and lives in its own file or an anchored entry. Messages, other entities, and humans reference it as ar://<type>/<id>.
  • Globally unique IDs. An ID is a type prefix plus a ULID, for example C-01K6Z3V8QX…. A ULID sorts by creation time and is unique without coordination. Filenames add a slug. Documents can show a short form: the prefix plus the last 6 characters. Every prefixed entity uses this format. In this document, NNNN in examples such as C-NNNN stands for the unique ID.
  • Prose describes the present. Records keep the history. This rule comes from PlayerADE9. The agent edits hubs, STRATEGY.md, and claim text in place. A claim keeps its status and evidence history in its frontmatter and in git. Experiments, Results, journal entries, evidence, and versions are append-only.
  • Close, don’t delete. A contradicted claim gets superseded_by or valid_to_version. The file stays.
  • Provenance everywhere. Each judgement cites the evidence, Result, or experiment that produced it. The workspace is a git repository, and the runtime merges and commits after every iteration. Thus, every change has a commit.
  • Currency. Every claim carries the game versions it is valid for. A game update marks older claims stale. See §3.5.

1 · Evidence

evidence/ + evidence/index.jsonl · ID: content sha256 plus platform id (episode id, XP request id) · episodic · immutable

Replays, XP results, logs, and artifacts. Index fields: sha256, kind (replay | xp-result | log | artifact | leaderboard-snapshot | game-source), source ids, game_version, policy_version(s), fetched_at, path.

Kind game-source: a citation of the game’s own code. Fields: repo, path, line range, pinned commit, and game version. It is the top evidence tier, S. See §3.5.

2 · Journal entry

journal/J-NNNN.md, one per iteration run · episodic · immutable after its iteration

Front matter: iteration, mode, started, ended, unit (one line), outcome (done | partial | dropped | failed, the same values as the card outcome), doctrine_version, refs[]. The body says what the iteration did, what it learned, and what changed.

Decisions section: every entry has a required Decisions section. Each decision has the decision, its reason, and refs. Each one is addressable as ar://journal/J-NNNN#dN. The completion check enforces the section. Doctrine rule 1 says which decisions go here. Proposed priority changes also go here, for a planning iteration to apply.

One ID per iteration run: each iteration run gets one journal ID from records new. IDs do not follow wall-clock ticks. Two concurrent iterations thus never share an ID.

Doctrine version: doctrine_version records the doctrine version that the iteration ran under. See §4.

3 · Plan

plan.md · working memory · written by planning iterations only

Sections:

  • Priorities: ordered, each with its reason. Priorities reference Topics.
  • Open threads: parked lines of work and what they wait on. A thread waits on an XP request, a help request, or a question.
  • Changed this session.

The plan holds no next actions. Next actions are cards in the work queue. Only planning iterations write plan.md. Other iterations record proposed priority changes in their journal Decisions section and create a planning card.

4 · Topic

research/topics/T-NNNN-<slug>.md · semantic + plan · description edited in place, history in git

A Topic names something to work on. Examples: improving accuracy, increasing last hits, winning faster, and cooperating better. The agent or the Preston interface agent can create one. Hypotheses tie to Topics as in PlayerADE4.

  • id, title
  • objective: what better looks like, in words.
  • metrics[]: the measures of progress, behavioural or outcome, each with its direction.
  • guardrails[]: metrics that must not get worse beyond a stated tolerance. See the decision rule.
  • origin: agent, or human via Preston with the inbound message ref.
  • priority
  • status: open | active | achieved | closed, with a reason.
  • hypotheses[]: many-to-many.
  • hubs[] and claims[]: related knowledge.
  • strategy_components[]: the parts of STRATEGY.md that matter to the Topic. These are any component IDs: goals, situations, skills, capabilities, rules, or adaptations.

Two kinds of goal. Topics are research and development goals. STRATEGY goals (the G layer) are in-game objectives of the policy. Aaron’s Goal layer covers both scopes10. Topics carry the development priorities. STRATEGY G carries the gameplay outcomes.

Proposed by Preston. An inbound steer can carry a proposed_topic. The agent creates the Topic or merges it into an existing one. Then it acknowledges with an ar://topic/T-NNNN ref.

5 · Hypothesis

research/hypotheses/H-NNNN.md · semantic · judgement state stored

  • id
  • statement: the mechanism, “X happens because Y”.
  • prediction: what we expect to observe if it is true.
  • topics[]: the Topics it addresses. Many-to-many.
  • parents[]: the hypotheses it refines or derives from.
  • source: the investigation journal entry or evidence refs.
  • lever: the strategy mechanism it acts on. The thrash guard checks it against refuted mechanism claims.
  • state, state_reason, experiments[].

States proposed → under-test → supported | falsified | abandoned. The file stores each state change with its reason and ref. under-test is derived from a running experiment.

6 · Experiment

research/experiments/E-NNNN.yaml · episodic + judgement · pre-registered

Pre-registration means the agent writes everything above results before any result exists.

  • id, hypothesis
  • parents[]: earlier experiments on the same hypothesis that this one redesigns. Empty for a first experiment.
  • mode: always experimentation.
  • lever
  • baseline: a version id.
  • change: STRATEGY component ids plus a one-line description. Exactly one conceptual change.
  • candidate: the version id, once built.
  • decision_rule: primary metrics, agent guardrails, the general performance guardrail, minimum completed episodes N, and opponents or seat design. It also records the δ and N used, with the version of the noise record. See below.
  • environment: game id, coworld version, game_version, manifest sha256.
  • xp_requests[]: handles for recovery.
  • results[]: refs to Results.
  • status: designed → built → uploaded → evaluating → reviewed. An evaluation that waits for credits has status awaiting-credits.
  • decision: {outcome: promote | hold | refute | invalid, reason, decided_at, refs}. The decision cites Results.

Lineage. A follow-up experiment on the same hypothesis with a changed design names the earlier one in parents. A re-run of the same design produces a new Result instead.

The pre-registered decision rule

A behavioural improvement must not produce a worse policy. But a slight loss in win rate is acceptable for a significant behavioural gain. The agent also sets its own guardrails to block reward hacking. The experiment takes its defaults from its Topic and from the game contract.

PartWhat it saysWho sets it
Primary metricsWhat must improve, behavioural or outcome. Each has a direction and a minimum effect.The agent, from the Topic’s metrics[]
Agent guardrailsMetrics that must not decrease, or not beyond a tolerance. They block gaming of the primary metric. Every behavioural primary metric needs at least one anti-gaming guardrail. A rate metric needs its volume counterparts. Example: when the goal is higher accuracy, shots fired and kills must not decrease.The agent, from the Topic’s guardrails[] plus its own additions
General performance guardrailThe game’s outcome metric can slip by at most a tolerance δ, and only when the primary improvement is significant. GotA: XP per 1,000 ticks and win rate. δ comes from measured noise.The game contract names the metric (§9). δ is computed. See noise calibration.

The promote decision stays with the agent. It can rest on a measured behavioural improvement, not only on a strict MMR or score gain. The submit tool checks that the experiment shows promote, that every guardrail holds, and that N is met against the current champion. The constants k, power, and alpha are configurable. See §10.

Noise-calibrated δ and N

A program computes δ from the noise of the game and the metric. δ is about 0.5 and at most 1 standard deviation, scaled to the planned episode count. δ and N come from empirical league data. Maintenance refreshes that data regularly.

  • The noise record. stats/metric-noise.yaml holds one entry per game version and metric. Each entry has the sample mean, the standard deviation, the per-episode variance, and the sample size. It also names the league and own-XP evidence behind it, and computed_at.
  • Its source. A deterministic script computes the record during maintenance. It reads league episodes and our completed XP Results. No LLM does the arithmetic.
  • δ, the allowed slippage on the general performance guardrail, is k times the standard error of the difference between candidate and baseline. The standard error uses the experiment’s planned episode count. By default k = 0.5, with a cap of 1.0.
  • Effect of δ. Noisier metrics and smaller evaluations allow more slippage. Larger evaluations allow less.
  • N, the minimum completed episodes, comes from a power calculation on the same record. N is the episode count that detects the experiment’s stated minimum effect on its primary metric. The defaults are 80% power at a 5% significance level. The game contract supplies a floor.
  • Significance test: a paired or matched bootstrap confidence interval on the difference. It needs no distributional assumption. The Result reports it.
  • Recorded at pre-registration. The experiment records the δ and N it uses, with a ref to the version of the noise record.

7 · Result

research/results/R-NNNN.md · episodic · immutable once written

A Result connects the evidence from one experiment’s XP requests with a write-up and an analysis. A correction is a new Result that supersedes the old one.

  • id, experiment, xp_requests[]
  • evidence[]: evidence refs.
  • policy_versions: baseline and candidate.
  • game_version, episodes_completed
  • metrics: primary, guardrail, and outcome values, with uncertainty. Each difference carries its bootstrap confidence interval.
  • validity: valid, or invalid with a reason. Worker failures and wrong seats are two such reasons.
  • analysis: a Markdown write-up of what was observed, the surprises, and the caveats.

9 · Claim

kb/claims/C-NNNN-<slug>.md · semantic · text edited in place, status and evidence history in frontmatter and git

One checkable assertion per file. The body states the assertion as prose about the present.

  • id
  • kind: mechanism | behaviour | strategy | opponent | platform.
  • status: hypothesis | belief | verified | stale | superseded | refuted.
  • confidence
  • evidence_grade: high | moderate | low | very_low. The linter computes it. See §3.5.
  • evidence[]: {ref, tier, direct, stance: supports | contradicts}.
  • revise_if: the observation that changes the claim.
  • relations[]: {type: supports | contradicts | refines | depends_on | undercuts, target}.
  • valid_from_version, valid_to_version, last_checked_version
  • supersedes, superseded_by
  • topics[], recorded

Refuted mechanism claims. A refuted claim about a strategy mechanism is a closed lever in the optimizer-seed sense7. Its revise_if is the reopen condition. The thrash guard checks new experiments against refuted mechanism claims.

10 · Hub

kb/hubs/<slug>.md · semantic · edited in place

A hub is an agent-facing, present-tense synthesis page. Examples: game mechanics, our strategy, opponent X, and the league meta. Every sentence cites the claims it rests on as [[C-NNNN]]. A hub never holds a claim that has no claim file.

Hubs follow the Hermes /learn pattern: a lean index entry that says “load this when …”12. Each hub carries its currency: the game version it was last verified on. The game extension’s docs seed the hubs.

Split and merge. A hub splits on size or on topic drift. Two hubs merge on overlap. The size limit is configurable and grounded in retrieval experience. The default is about 2,000 tokens per hub. See §10.

  • Drift. The linter flags a hub whose cited claims form weakly connected clusters, with few links between the groups. The hub is a split candidate.
  • Overlap. The linter flags two hubs that cite mostly the same claims. They are a merge candidate.
  • Maintenance creates cards for flagged hubs.

10a · Opponent model, part of an opponent’s knowledge

kb/opponents/<opponent-id>/STRATEGY.md · semantic · edited in place

A STRATEGY-like model of one opponent’s observed behaviour. It uses the same layers as our STRATEGY.md. Every element carries provenance inferred and evidence refs. The opponent’s claims and hub hold its strengths and weaknesses. The model holds its inferred strategy. Scouting writes both with opponent-profile. See §5.3.

This matches the inferred_opponent packages in Aaron’s semantic IR13. There, an inferred opponent package holds observational hypotheses and forecasts. It needs no executable and must not fabricate one.

12 · Lesson

A lesson is about how to research: method, not the game. Lessons are a separate store from claims for this reason. 3.2 Relationships

  • Claims, Results, and Hypothesis.source cite Evidence. Hubs cite Claims.
  • Topics and Hypotheses link many to many. A Topic gives an Experiment its default metrics and guardrails. A Topic also relates to claims and hubs, and to STRATEGY components.
  • An opponent’s hub links to its Opponent model. Each element of the model cites evidence, with provenance inferred.
  • One Hypothesis has many Experiments. One Experiment has many Results.
  • An Experiment points to two Versions: baseline and candidate. Versions form a DAG through parents.
  • Experiment.change names STRATEGY components.
  • Experiment.decision cites Results. It updates Hypothesis state, adds or revises Claims, counts Lesson recurrences, and sets component status. A refute can produce a refuted mechanism claim.
  • Refuted mechanism claims are the thrash guard. A new experiment on the same lever needs evidence that meets the claim’s revise_if.
  • The Plan references Topics, open Hypotheses, Experiments, and Messages.
  • A Journal entry references everything its iteration touched, and it records its decisions.
  • Work-queue cards point at entities through refs[], and a completed card points at its journal entry. No entity depends on a card.

3.5 Knowledge base: claims and hubs

  • Atomic claims hold the knowledge. Hubs are readable synthesis pages that cite claims.
  • A linter, not the LLM, computes each claim’s evidence grade from source tiers.
  • Stale claims stay in the knowledge base, marked. Compaction archives the longest-stale claims when too many are stale. A fresh session starts from a generated index.

The knowledge base is plain Markdown in the workspace git repository.

Why this shape. One claim per file is the unit of verification, as in nanopublications15. Thus, a page rewrite never loses a citation. Git-backed Markdown with a small index follows Letta context repositories16, and the index, log, and lint loop follow the LLM Wiki pattern17. Validity fields and close-don’t-delete come from the Graphiti temporal model18. Agentic grep generally beat vector retrieval on LongMemEval19, so the agent searches with rg first. Evidence strength and verification

A linter computes evidence strength. The LLM never computes it. The linter stores the computed evidence_grade in the claim file, so readers do not recompute it.

SGame source at a pinned commit, cited as path:line-range@sha.
AOfficial docs or changelog.
BA controlled experiment: A/B, fixed seeds, n reported.

A second axis adjusts the grade, in the style of the Admiralty code20 and GRADE21. Independent corroboration raises it. Open contradictions and indirectness lower it. A code citation whose effect the agent infers, not reads directly, drops one tier.

Any kind—D or E evidence alone. Such claims stay belief.

Currency

  • Two times. Valid time is the game version: valid_from_version, valid_to_version, last_checked_version. Transaction time is git history.
  • Stale marking. On a game version change, the linter marks claims with an older last_checked_version as stale. Stale claims stay in the knowledge base and in index.md, marked.
  • Mechanical renewal. For a code-cited claim, the linter diffs the cited lines in the game repo between versions. If the lines did not change, it renews last_checked_version. If they changed, it opens a re-verification item.
  • Compaction. When 10% of claims are stale, maintenance compacts stale claims down to 2.5%. It archives the longest-stale claims first. Each one moves to kb/archive/ with its status unchanged and its links kept. Git keeps everything.
  • Compaction guards. Never compact a claim stale for less than a minimum age, by default 14 days. Never compact a claim with a pending re-verification card. Never compact a claim that a live hub, Topic, hypothesis, or experiment cites. Reason: a game update can make a large share of claims stale at once. Without the age guard, compaction removes them before re-verification. See §10.

Retrieval for fresh sessions

  1. Read kb/index.md. It is generated. It lists the hubs and one-line claim summaries by topic, with status and grade, within a token budget.
  2. Read the hub for the task.
  3. Follow links to claims, and search with rg.

The generator also writes backlinks and contradiction lists. A search index is optional and rebuildable. It becomes useful only past roughly 500 claims. Candidates are qmd22 and Basic Memory’s SQLite index23.

Tooling

Adopt conventions and small tools. Build only three things:

  • A frontmatter JSON Schema.
  • A knowledge-base linter. It computes grades and promotion eligibility. It checks link resolution and orphans, staleness and code-citation diffs, hub sentences that cite claims, and unresolved contradictions. It also flags hubs to split or merge.
  • The index and backlink generator.

Off the shelf: ripgrep, check-jsonschema, and python-frontmatter. The last two come from the author’s own knowledge, not from the research in Appendix C. Claim and hub files use Basic Memory line syntax (- [category] fact, [[link]])23. Thus, Obsidian or Basic Memory can open the knowledge base.

Hermes built-in memory

The agent uses no external memory provider. MEMORY.md stays tiny: a pointer to kb/index.md plus a few harness and tool notes. The companion document has the details.

3.6 The work queue: a thin layer outside the ontology

  • The work queue holds next-action cards only. Each card is one bounded unit of work for one iteration.
  • A card is Pending, Claimed, or Completed. Nothing else.
  • The queue is not research state. A card points at entities. It never holds them.

The queue is only a work queue. It is not a board of research ideas or Topics, and it stores no hypothesis or experiment lifecycle.

States Pending → Claimed → Completed. A card that cannot proceed is Completed with an outcome note: done | partial | dropped | failed. Where needed, the iteration also creates a follow-up card or sends a help request. A card never waits.

Card fields

  • title: the action, in the imperative.
  • mode: investigation | scouting | experimentation | maintenance | planning.
  • why: one line.
  • refs[]: ar:// refs to the workspace entities that the card concerns.
  • created_by: planner, iteration J-NNNN, runtime script, or an inbound message id.
  • priority: P0 to P5. See card priority.
  • On completion: outcome and a journal ref.

The queue is not research state. Topics, hypotheses, experiments, Results, claims, and decisions live only in the workspace. A card points at them through refs[]. Thus, a lost queue loses no research. The planner can rebuild the queue from the workspace: open Topics, plan Priorities, and experiments that await review. 3.7 Concurrent iterations

Up to 2 iterations run at the same time in v0. The number is configurable. Several evaluations, each a batch of XP requests, can be in flight at the same time. A credit refusal pauses an evaluation. See §5.4.

  • A worktree per iteration. Each iteration claims one card. It works in its own isolated copy of the workspace, a git worktree.
  • Serial merge. When an iteration completes, the runtime merges its changes into the main workspace, one merge at a time. A merge conflict creates a reconciliation card.
  • One writer per entity. An iteration creates new entities freely. It changes an existing entity only when its card’s refs name that entity. If two Pending cards change the same entity, the planner merges them or orders them.
  • No shared ID allocator. IDs are unique without coordination. See the ID format. Thus concurrent iterations need no allocator. records new creates each ID and validates its format.
  • Generated files. The runtime regenerates kb/index.md, the backlinks, and the contradiction lists after each merge. Iterations never edit them.
  • Append-only logs. kb/log.md merges cleanly. Each iteration writes its own journal entry, one per iteration run.
  • A promotion lock on STRATEGY.md. An experiment builds its candidate from a named baseline version in its own worktree. Only a promote decision changes the champion STRATEGY.md, and only one promotion runs at a time. If the champion changed during evaluation, the experiment re-evaluates against the new champion before it can promote. The promotion rule requires a measured gain over the current champion.
  • One writer for plan.md. Only planning iterations write it. Other iterations record proposed priority changes in their journal Decisions section and create a planning card.

4 · Doctrine: the agent’s standing instructions

  • 25 rules in seven groups. They ship as doctrine/research-agent.md, which becomes the workspace AGENTS.md.
  • Adapted from optimizer-seed’s constitution, with decide-and-record in place of propose-and-pause. co-gas supplies the evidence gates.
  • Each rule has a stable ID, D-01 to D-25. The doctrine has versions and improves from evidence.

The doctrine adapts optimizer-seed’s constitution24 and adds co-gas’s gates25. The main adaptation is decide-and-record in place of propose-and-pause, because no human approves each step.

Each rule’s ID is D- plus its number. For example, rule 23 is D-23. Evidence points at rules by these IDs.

Authority and autonomy

  1. Decide and record. No approval is needed for XP, uploads, or submissions. Record every decision with its reason and refs. Experiment decisions go in the experiment. Submissions go in the version record. Acknowledgements go in the outbox. Every other decision goes in the journal entry’s Decisions section.
  2. Inbound steering outranks your own plan. Acknowledge every inbound message: applied, declined with a reason, or noted.
  3. Act only as the configured Player. Never switch identity.

Evidence

  1. The live field is the only oracle. Local runs are for debugging, not for decisions.
  2. Pass the replay-analysis gate before you change strategy. The gate needs a completed replay with hash and mechanics version verified. A committed tool decodes it. Actions map to stable player IDs. A concrete “before” metric and a named cause are recorded. If the replay cannot show the cause, add instrumentation first25.
  3. Only completed, inspected XP counts as evidence for promotion. Pending rows, local wins, and “the version exists” do not count2526. A promotion also needs N completed episodes and every guardrail satisfied against the current champion.
  4. No claim without a citation. The linter grades the evidence. A claim with only D or E evidence stays a belief, with confidence and “revise if”.

Experiment discipline

  1. One conceptual change per experiment24. Take the default metrics and guardrails from the hypothesis’s Topics.
  2. Pre-register the decision rule before results exist. Name the primary metrics, the agent guardrails, the general performance guardrail, and N. Never edit the rule after. Give every behavioural primary metric at least one anti-gaming guardrail. A rate metric needs its volume counterparts. Example: accuracy needs shots fired and kills.
  3. Check refuted mechanism claims before you propose an experiment. Reopening a lever requires evidence that meets the claim’s revise_if.
  4. Never wait on XP inside a session. Record the handle, complete the card, and move on. The runtime creates the review card when the XP completes27.

Session contract

  1. Start by reading your card, its briefing, the Topics the card names, and kb/index.md. A planning iteration reads all of plan.md. Do the card’s one bounded unit of work in its mode. End with card completion: journal with its Decisions section, acknowledgements, valid records, follow-up cards, and the card outcome.
  2. Respond to a stuck signal. When the briefing reports one, change course, explain in the journal why you are not stuck, or send a help request.

Knowledge hygiene

  1. Prose describes the present. History goes in records. Prose means hubs, STRATEGY.md, and claim text. Claim status and evidence history go in frontmatter and git.
  2. Close, don’t delete. Give a contradicted claim superseded_by or valid_to_version. Keep the file.
  3. Every hub sentence cites claims. A hub never holds a claim that has no claim file.
  4. Lessons graduate on recurrence. Refuted mechanism claims say what reopens them in revise_if.
  5. Self-written skills go to skills-proposed/. Send a suggestion for each new or patched skill. Do not use it as an adopted skill until a human replies.

Communication

These rules also appear in doctrine/communication.md.

  1. Findings first. Answer the question first. An unanswered question stays owed. Teach before you ask: never ask for a strategic choice built on mechanics you have not explained28. Keep the backstage backstage. Never send an empty message24.
  2. Point, don’t restate. Messages reference entities with ar:// refs. Send one highlight per event that §5.7 lists.

Cards and the shared workspace

  1. Work only on your claimed card.
  2. Create follow-up cards for further work. Do not do that work in this iteration.
  3. Change only the entities that your card names. Create new entities freely.
  4. Never edit generated files: kb/index.md, backlinks, and contradiction lists.
  5. The champion STRATEGY.md changes only through a promotion.

Doctrine versions and proposals

  • Violation counts. The runtime counts violations per rule. Completion checks and signals find them. For example, a change to an entity that the card does not name counts against D-23.
  • Doctrine proposals. Some lessons recur and concern how the agent behaves. These become doctrine proposals. A proposal is a diff in doctrine-proposed/ with its evidence.
  • Review. Each proposal goes to a human as a suggestion message, in the same flow as skill proposals. The human adopts, rejects, or revises it.
  • Versions. An adopted change bumps the doctrine version. Each journal entry records the doctrine version it ran under. Thus a reader can compare effects before and after a change.
How is this enforced? The runtime checks each card completion and computes the signals. The companion document, Autoresearch Runtime, Packaging & Integration, describes how.

  • Each iteration runs one card. Up to 2 run at the same time in v0.
  • A hypothesis lives across several iterations and cards. XP runs while other iterations do other cards.
  • Review writes a Result before it decides.

5.1 Iteration start every iteration

  1. Claim the card that the runtime offers. Read the card: its title, mode, reason, refs, and priority.

5.5 Review and decision

  1. Start from a review card. The runtime creates it when the experiment’s XP completes.

9 · The game contract: what a game supplies

  • Core never names a game. A game extension in games/<game>/ supplies everything game-specific.
  • A missing binding is a reported gap, never a silent fallback.
  • The contract sets the outcome metric and a floor for the minimum episode count N. Measured noise sets δ and N.

The contract follows optimizer-seed’s MIXIN.md31 and its rule that core skills never contain game conditionals24. A game extension supplies five things:

  • Bindings: build, local-check, upload settings, evaluate (XP template + metrics), and replay-inspect.
  • Promotion settings: outcome_metric, and min_episodes as the floor for N. The general performance guardrail and the submit check use them. δ and N come from the noise record.
  • Strategy vocabulary: the game’s primitives, limits, and host data for the STRATEGY.md layers, plus which layers apply. GotA has no COM layer.
  • Seed workspace: a baseline STRATEGY.md, initial hubs from the game docs, and initial claims with citations. For GotA, the baseline is v13 described semantically.
  • Game skills (the five bindings) and extra reference types, for example a GotA replay segment.

Appendix D · Alternatives considered

  • Wiki pages as the unit of knowledge. Citations get lost in rewrites. A page cannot supersede half of itself.
  • Graphiti as the source of truth. At most a rebuildable index, and only if claims reach thousands.
  • Any Hermes memory provider. See the last row of the table in Appendix C.
  • LLM fact extraction into a vector or graph store, as in Mem0 or Cognee. Silent merges defeat provenance.
  • Separate knowledge-entry, belief, and closed-lever entities. One claim entity with a status and a computed grade covers all three.
  • Topic as a free tag on hypotheses. A tag carries no metrics, guardrails, or origin. Thus neither the agent nor Preston can name work with it.
  • An always-pending planning card. A fixed schedule grooms the queue at a regular rate. The queue-growth signal adds planning when needed.
  • At most one evaluation in flight. Credit refusals need handling anyway. Pausing an evaluation as awaiting-credits protects credits without serial evaluations.
  • Sequential IDs from a shared allocator. Concurrent iterations need coordination, and IDs from two workspaces collide.
  • A fixed slippage tolerance δ in the game contract. Games and metrics differ in noise. Measured noise gives each metric its own δ.
